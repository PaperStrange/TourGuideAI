### 1.3 三问

**① 他看到的第一个画面是什么。** 它是这个状态的纯函数：

```
首帧 := render(walker.cell, street.profile, anchors, derived := ∅)
anchors := guide.json 的 6 条 inSceneWindow 记录 ∪ doors.json 的 10 个门洞
           （各带真实名称、坐标、逐字段 valueKind、source_url、verified_at）
```

**世界层（canvas）**：空白底 + 街道中线 + 走者。走者必须是**与自己的轨迹不同形**的标记（轨迹=方块，走者=带朝向的窄标记；朝向 = 上次移动方向，`t=0` 朝东）。现在两者同色相同形（`#1F6B3A` vs `rgba(31,107,58,.30)`），走三步以后"我在哪"只能靠亮度分辨。

**HUD 层**：只有四个信息位（§1.4）。

**文档层**：现在首屏下方那张 10 行 × 8 列的门表**必须移出首屏**（默认折叠）。它是调试面，不是游玩面；留在首屏等于给受试者一个任务日志，而我的角色约束明确拒绝任务日志。

**首帧里允许出现的字符串**（取代"不许写提示语"这句口号，可机械复核）：

> **首帧里的每一个字符串，要么是界面常量（单位符号、数字、`·`、`/`），要么是逐字读自事实层的值（真实名称、`source_url`、`verified_at`、`valueKind`）。**
> **不得出现祈使句、目标说明、颜色图例、键位说明（V-B 变体除外）、写死的时间或价格。**
> 判据：**若事实层改了而某个字符串会变错，它就不许是字面量。**（这就是"存句子等于给过期的营业时间穿上友好的外衣"的机械形式。）

**② 第一个可执行动作是什么。** `↑ ↓ ← → / WASD`。**第一个动作不需要是 E**（见 §1.8 的两段判据）。

**③ 世界如何回应。** 回执**不是精灵移动**，是下列之一：
- HUD 上的距离数字变小（`→ 20.7 m` → `→ 19.7 m`）；
- 被点名的目标换到另一个锚点（到达后**自动**发生，不需要再按键）；
- 走进任一锚点 1.5 格内 ⇒ 该锚点切到"已到过"，且 `街上 n/6` 或 `门洞 n/10` 加一。

`E` 在 1.5 格内按下 ⇒ **门口回执**：
1. 真实名称（`nameJa`；有 `nameZh` 就并置——**并置不是翻译按钮**，是两个都已溯源的字段）；
2. 位置：沿街 `x m` · 偏离中线 `±m`；
3. **它是怎么被知道的**：逐字段 `valueKind` + `source_url` + `verified_at`；
4. **两栏状态，分开显示**：`你到过`（玩家行为）· `值已核`（来源属性，只对 `observed` 点亮）。**"你到过"绝不给一个 `licenced` 名称背书成"我们核实过"**——`design-core` §8.2.1 ④ 的风险只能靠分栏防住，不能靠一句纪律防住；
5. 门洞额外：`surface`（measured / unmodelled）+ 实测进深 + **「门位是 `authored`：没有任何人观察过它」**；
6. 南侧门洞：`内容开发中` +「本版本未建模，不是布局示意图」（已有，一字不改）。

**这条回执就是"游玩轨迹 = 攻略"的最小完整形态**：名称、位置、来源、玩家行为、以及"哪些话我们不敢说满"，在同一行里。

### 1.5 摄像机与手感参数（`export-guard` 划归我的部分）

| 参数 | 我的判断 | 理由 |
|---|---|---|
| **lerp 0.1** | **不做** | ① 页面**没有帧循环**（`requestAnimationFrame 0`），而 `geo-contract` 已裁定：**模拟步进不得由挂钟或帧间隔驱动**；② 现有断言要求"同一 `scene.bin` 两次渲染产出**逐字节相同**的帧"，逐帧插值会打破它；③ 1 格 = 1 m、一次按键 = 1 格，插值只是给一个本来就离散的动作加烟雾 |
| **deadzone 192×96 px** | **做，但换成整数格**：`deadzoneX = round(192/(32·zoom))`、`deadzoneY = round(96/(32·zoom))` ⇒ zoom 2 下 **3 × 2 格** | 像素值随 zoom 变，格值不随；且摄像机位置必须是整数格（`roundPixels`）。**这仍然是规格的数，只是换了单位** |
| **跟随规则** | 走者**永远不出画面**（硬规则，可断言）+ **朝目标偏置**： `dir = sign(next.cellY − walker.row)`；`camTop = clamp(walker.row + dir·floor(spanY/3) − floor(spanY/2), 0, H−spanY)` | 偏置把"北墙要盲走 8 步"降到 **5 步**（居中跟随要 `walker.row ≥ 19`，偏置后 `≥ 16`）——**这是能在 zoom 2 下拿到的最多** |
| **⚠️ 硬事实** | **走者 + 门行不可能同时在 zoom 2 的窗口里**：两者相隔 13 行 > 可见 11 行。**这不是调参能解决的** | §1.6 |

### 1.6 三条出路的裁决（`export-guard` 列出、我裁）

| 出路 | 裁决 | **依据（都是规格内部的，不是我的偏好）** |
|---|---|---|
| **1 · 默认改 zoom 1** | **拒绝（三条独立理由）** | ① 附录 L31 给 zoom 1 的用途原文是「**只用于拍照/攻略截图与调试地图，静止**」——**它不是游玩档**；② 附录 L22 的「12 px 字形 → zoom 2 屏上 24 px」是**字形可读性的唯一一次定案**，zoom 1 下 12 px 字形只有 12 px，**模糊墨团与清晰汉字在屏上无法区分，我角色记忆第二条的机制当场失效**；③ **🔴 我算出来的那条**：zoom 1 的窗口是 `40 列 × 23 行`，出生时 `camTop=0` ⇒ **行 0..22**。**北侧 7 扇门在 row 24，全部仍在屏外；而南侧 3 扇占位门在 row 0，全部进屏。**<br>**⇒ zoom 1 不是"看得见门"，是"只看得见那三扇按用户裁定会回答『内容开发中』的门"。** 这是最坏的一种可见性：**看得见错的那个。**（三条里没有一条是我的偏好，前两条在规格里，第三条是算术。） |
| **2 · 镜头保证最近的门在窗口内** | **在算术上不可能，但它的"可能那一半"我采用** | 出生时走者 `row 11`、门 `row 24`，相隔 **13 行 > 可见 11 行**。**任何规则都无法同时装下两者**；能装下两者的规则必须把走者移出画面，那更糟。**所以"偏置"（§1.5）是这条的唯一可行形态，剩下的差距交给 S1** |
| **3 · 朝向门的边缘指示器** | **采用，而且它不是备选，是唯一幸存者** | 由前两条推出：**在 zoom 2 下，玩家在门进画面之前不可能看见门。** 因此"目标在哪、还有多远"**必须**由 HUD 承担（S1），而世界的回执是"距离变小 → 立面从画面上缘滑进来 → 凹进可见 → E" |

**⇒ 结论：默认 zoom 保持 2，加 S1，加偏置，不做 lerp。** 这一条同时保住了字形机制（24 px 可读）和"看得见目标"。

**⚠️ 而由此得到一条给 `export-guard` 的陷阱记录**：

> **"让门可见"这个动作本身会把玩家引向占位门。** 在当前页面（16 px/格、96×40 窗口）与出路 1（zoom 1）下，出生瞬间**可见的门恰好是南侧那 3 扇**（`row 0`），而**北侧 7 扇有 3 m 室内的门一扇都不可见**（`row 24` 超出窗口）。**⇒ 任何"先把门弄进画面"的改动，在没有 S1 指示器的情况下，第一个后果是玩家走向三扇会回答「内容开发中」的门。**
> **而它【只被避开了一半】**：`next` 的第一个目标确实是横断歩道（有来源的真实地点）而不是门——**但那只是第一个**。第 2、3、4 个目标在纯距离规则下仍然是那三扇占位门（§1.7 的表）。**⇒ 真正避开它的是 §1.7 的 `eligible` 规则，不是"纯函数"本身。** 这也是为什么 **S1 与 `eligible` 必须和"让东西可见"同时上线，不能分两次做。**

### 1.6b v1 → v2 的更正（我自己的错，写下来）

**我 v1 的首帧规格是按磁盘上那个页面算的**（`ZOOMS=[2,4,8,16,32]`、`zoomIdx=3`=16 px/格、`VIEW_TILES_X=96`、`VIEW_TILES_Y=40`），于是写下"首帧里 10 扇门全部可见"。**那是旧代码的窗口，不是规格的窗口**——`bake-viewer.mjs` 的新摄像机已经把默认定在 zoom 2（20 × 11 格）。
**⇒ 我 v1 的结论（"门都在首帧里"）不成立；首帧是 0 格内容。** 我据那个错误窗口还推过一个次生结论——"最近的红点是一扇占位门（`D-S1` 曼哈顿 30 < `D-N1` 31），所以玩家会先走到占位门"。**在 zoom 2 下这个论断也不成立（他看不见任何门）**；而在 zoom 1 下它成立且更糟（见上）。
**这个错误的形状与 `export-guard` 把 zoom 读反是同一个：用一个未核的默认值推出了结论，而结论看起来完全合理。** 两来源纪律能防住它——**我 v1 只有一来源（当前页面）。**

### 1.7 数据形状（交给 `export-guard`，不是实现）

```jsonc
"anchors": [
  { "kind": "place",                 // "place" | "doorway"
    "id": "kyoto-shijo-crossing-karasuma-east",
    "nameJa": "四条烏丸交差点 東側横断歩道", "nameZh": null,
    "alongStreetM": 20.72, "acrossStreetM": -8.88,
    "cellX": 20, "cellY": 11,        // nearby 记录今天没有 tileX/row —— 见 §9 第 3 条
    "nameFieldKind": "licenced",     // 逐字段，不按记录
    "verifiedFields": [],            // 直接搬 guide.json 的 verified
    "sourceUrl": "https://www.openstreetmap.org/node/2737069286",
    "verifiedAt": "2026-09-29" }
]
```
- `derived` / `read` 是**两个只增的扁平 `Set<string>`**，key 即 `id`。**它们同时是进度、存档与攻略可信度来源——但三处用途共用一个集合，不等于三个分数可以相加。**
- **存档就是这两个集合**（`t=0` 全空）。**它们不含任何句子、不含任何时间。**
- **`next` 的定义（唯一一处，v2 已更正）**：

  ```
  eligible := { a : a ∉ derived  ∧  a.modelled !== false }
  next     := argmin{ 到 walker 的格距 : a ∈ eligible }      // 平局取 alongStreetM 较小者
  若 eligible = ∅ 则退回全集（仍要点名，不得空转）
  ```

  **无优先级表、无剧本、无持久化。**

  **`格距` 的定义（v2.3 补，因为 export-guard 发现我那张表和我的正文不一致）**：
  > **`格距` = 曼哈顿格距（`|ΔcellX| + |ΔcellY|`），参照点是【walker 的当前格】，且每一步重算。**
  > **为什么是曼哈顿而不是欧氏**：移动只有四个方向、一次按键 = 1 格，**所以曼哈顿才是"要走几步"**；欧氏会**少报**要走的路。**而这个项目已经为同一个错误付过一次代价**：`D-53`/P3 的 `L09` 就是"声明 15 分是直线距离，而規約要的是道路距離"。**游戏内用欧氏，等于把那个缺陷按比例重演一遍。**

### 1.10 出生点：**不换坐标，换来源**（SOW §12⑫ 的答复）

**问：出生点该不该换？若该，挂在哪条判据上？**

**答：不换。换的是"它为什么在那里"，并且加一条能失败的断言。**

**理由（两条，都是算术）：**

1. **换 x 修不了首帧。** 我按 profile 反算了：**街上 `row ≥ 19` 最早出现在 `x = 700 m`**（因为街道自己在走廊里向北漂），**而 10 扇门全部在 `x = 18..38`**，`row 0` 与 `row 24`。**⇒ 在街上的任何位置，zoom 2 都看不见门。** 反过来：把出生点挪到 `x ≈ 28`（block 0 正下方）也一样看不见——**首帧的空是"垂直方向 13 行 > 可见 11 行"造成的，不是一个位置的属性。**
   **⇒ 所以 SOW §12⑫ 的措辞（"它正好落在世界上最空的地方"）会让人以为挪一挪就好。不会。唯一能让首帧出现门的位置是离开街道、站到立面前（`row ≈ 22`）——那等于让玩家从一栋楼门口而不是从四条烏丸开始，而"行程从四条烏丸开始"是本项目唯一有来源的起点。**
2. **`x=0` 有可指认的身份，而它缺的是"被决定的形态"。** `x=0` 就是冻结的 `ORIGIN`——契约把它定义为「**四条通 几何中位于四条烏丸以东的最西点**」，也就是**四条烏丸**。所以"你从四条烏丸开始"是**可核的**。它现在的问题不是位置错，是**它的值是从"沿街走通"那条无头断言的 `xStart=0` 默认值里继承来的**——**产出值的过程 ≠ 决定值的过程**，与本项目其余几处形状相同。

**⇒ 该挂的判据（一条，能失败）：**

```
SPAWN.cellX := 0                       // = 冻结 ORIGIN 的沿街位置（四条烏丸）
SPAWN.cellY := streetRowAt(profile, 0) // = 11，来自 street.profile（observed 几何）
断言：把 walk 的 xStart 改成 5（或任何 ≠0），SPAWN 必须【不变】。
     ⇒ 证明 SPAWN 与 walk.path 相等是巧合，不是依赖。
```

**这条断言就是本仓库反复付代价的那个形状的解药**（`D-12` / `D-44`：`FACADE_DEPTH_M` 派生自无关的冻结常量、`SCENE_VERSION` 在两个文件里各定义一次）。**修一次，`export-guard` 在 `task-24` 里顺手就做了**（它本来就要动 `bake-viewer.mjs` 里的 walker 初始化）。

**而 `task-24` 真正要改的是另外两件**（都在本规格里，优先级高于出生点）：**① §1.7 的 `eligible` 规则**（否则玩家的第 2–4 个动作全落在占位门上）；**② S1 与偏置**（否则首帧之后仍要盲走 5–8 步）。**⇒ §12⑫ 不必等用户裁定，它是一个我可以在规格里定死的实现决定。**

## 2 · 首帧的可见性边界：真实名称「存在 vs 验证」（Lead ⑤）

**冲突**：我的约束说「真实名称从第一眼就应该可见，被收藏的应该是**验证**而不是**存在**」；`design-core` L61 说「玩完就得到一张记录自己今天干了什么的卡」。**全看到会让"发现"失去意义；藏起来会让攻略的起点不是现实。**

**我的边界（一条，机械可查）：**

> **世界在第一次绘制时显示全部【有来源且走得到】的真实名称——存在不设门槛。**
> **任何"已验证 / 已核实"的标记只能由玩家的行为点亮，且**首次绘制不得点亮任何标记**。**
> **而"这条街上之外的 16 处"必须以计数形式在场（`街外 16（只能读来源）`），不得隐藏、不得假装不存在。**

**我认为这个冲突是假冲突，理由是**：**在本设计里"发现"从来不是"发现某个地方存在"，而是"发现关于它的哪个说法是真的"。** 一张真实的旅游地图本来就印着每个地名；它印不出的是"今天开不开、多少钱、门在哪一侧、这个名称是谁说的"。**藏起存在只会让游戏不像现实，不会让发现变多。**

**而"走不到"必须是可见的**：`GAP-SCENE-WINDOW` 是 5 条 stops + 11 条 nearby。若游戏只显示走得到的 6 处，玩家会以为这条街只有 6 个地方——**那正是 `design-core` L79–80 说的"游戏世界即事实"被自己的试验台限缩的时刻。** 所以第三栏（`街外 16`）不是装饰，它是这条诚实性的唯一出口。

**可机械化的那一半**（挂到已有断言器上，见 §8）：

> **⚠️ 更正（v2.2，我的第三个错）**：我原来写的是「**首帧渲染出的真实名称集合 = 事实层里 `inSceneWindow` 的名称集合**」——**那条判据与我自己的 §1.3/§1.4 矛盾**：我的首帧规格里**锚点只有形状、没有名字**（只有 S3 显示**一个**名字），而"6 个名字同时出现在首帧"**就等于我明确拒绝的任务日志**。⇒ **那条判据要么不可达、要么逼出一个任务日志。** 形状与我的前两个错相同：**用一个没核过的假设（首帧上有什么）写判据。**

**正确的形式——名称的可见性【不得是 `derived` 的函数】**：

```
对每个锚点 a：  visible(a)  与  derived  无关        // derived 只点亮【标记】，不改变【名称】
断言：把 derived 设成全空与全满，两次渲染出的【名称集合】必须相同（标记集合当然不同）
```

**两个状态、一次比较，不需要改数据，也不需要首帧上有一张表。** 这条才是我 §2 开头那句话的准确含义：**"真实名称从第一眼就应该可见"= 最近的那个名字在第一眼就在屏上（S3 现在就有）；其余的名字随着走近而出现，而【任何名字都不被进度门挡住】。**

**⇒ 而"存在不设门槛"的第二个出口是 S2 的第三栏**：`街外 16` 必须以计数在场——**它保证"走不到"不被静默成"不存在"。**

> **⚠️ 一条我要留在这里的立场（因为它在别处被提过要改）**：有人提议**用"能力清单（能画／不能画）"替代 (c) 差分烘焙**。**我不同意**，因为它答的是另一个问题：
> - `(c)` 问的是**一条被渲染出来的字符串是不是从事实层派生的**（渲染路径**输入**的性质）；
> - "能画／不能画"问的是**渲染器有没有这个本事**——**一个能画任意字符串的渲染器，"能不能画'按 E 开门'"的答案是"能"，它对"这句话该不该在"一个字都没说。**
>
> **而若理由是「能让脚本数的事就不该让人数」，那条理由用错了地方**：**本节的防伪条件已经把 `(c)` 的字段清单变成"从渲染路径里抽出来"——脚本数，不是人数。** 那条原则与我的条件是**同一条**。
>
> **唯一可接受的删法**：理由写成「**`(a)`+`(b)` 已足以抓住机制（硬编码的句子过不了闭集白名单），而 `(c)` 的 fixture 会随信息位增长而腐化**」，**并回答：删掉 `(c)` 之后，谁负责发现"白名单被顺手加了一项"？** 答不出人，就别删。

### 2.1 「引导层不得持久化散文」的机械形式（**不需要改真实事实层**）

**规则**：**首帧 + S1–S4 四个信息位里出现的每一个字符串，必须在生成页面里有且仅有一个来源**——(a) `ALLOWED_UI_STRINGS`（闭集），或 (b) 渲染时逐字取自 payload 的值。

**检查三段，全部机械，全部用已有入口：**

| # | 检查 | 怎么做 | 为什么它便宜 |
|---|---|---|---|
| **(a)** | **静态 · 白名单** | 首帧与四槽代码路径里的字符串字面量 **⊆ `ALLOWED_UI_STRINGS`**。每条必须带**类别 + 来源**：`unit`（`m`）· `separator`（`·` `/`）· `field-label`（`最近` `街上` `门洞` `街外` `东行`——"这个数是关于什么的"）· `state-label`（`你到过` `值已核` `待确认`）· `placeholder-by-ruling`（`内容开发中`，**必须引用户裁定原文**） | **闭集里没有"祈使句"这一类** ⇒ 想加"按 E 开门"，diff 上无处安放。**这就是守卫**。声明住在被跟踪的 `bake-viewer.mjs`（同 `opener-contract` 的做法：声明在脚本里，序列化形式才是派生物） |
| **(b)** | **动态 · 集合比较** | `t=0` 实际渲染出的字符串 \ 白名单 **⊆ payload 里逐字存在的值** | 纯读，不跑实验 |
| **(c)** | **差分烘焙（"若事实层改了它会变错"的可执行形式）** | 用**另一份 payload**（fixture）再烘一次页面，比较两次 `t=0` 的字符串集合：**变了的** = 事实层派生（合法）；**没变的** 必须在白名单里；**不在白名单又没变的 = 持久化散文，判失败**。<br>**fixture 的契约**：它必须改掉四个信息位可能显示的**每一个**事实层字段（名称 ja/zh · `source_url` · `verified_at` · `valueKind` · 三个分母 · 位置与距离）。**若列不出这些字段，说明信息位规格本身还不完整**——这是副产品检查。 | **`bake-viewer.mjs --doors <f> --opener <f> --out <dir>` 与 `check-viewer.mjs --doors/--places/--opener` 已经存在**（`iteration/viewer/README.md` 的 fire drill 入口）。**不新增工具，不改真实事实层** |

**执行者 = `export-guard`**（它拥有 bake 与那三个脚本）；**判读者 = `fact-verifier`**（它判"不在白名单又没变的字符串"是否真的是散文）。**它仍然不是门**（R2′ 第五类）：一条挂到已有断言器上的断言 + 一次 fixture 烘焙。

**弱点我写下来**：**`field-label` 是唯一能藏提示语的类别**（有人把槽位标题写成"按E开门"）。补一条窄的、fail-closed 的词表即可——**我们自己的中文 UI 文案是我们写的，不是多语言内容**，所以这里没有 SOW §8.2.2 ② 那种跨语言失效问题：**条目不得含操作动词**（`按` / `点击` / `请` / `去` / `走` / `看` / `试` / `使用`）。**假阳性由人复核——与导出边界扫描器同一条纪律（假阳性率是要监控的指标，不是要消灭的 bug）。**

## 3 · 那条不对称命题的边界（Lead ①）

> **「游戏越成功地像个游戏，导出的那一天就可能越糟。」**

### 3.1 这一版为什么不引入截止压力——**不是"以后再说"，是今天引入就必须编数**

1. **走廊内有来源的"时刻" = 0 个**：`hours` 非空 3/22，那三处分别在 `row −405` / `row −969` / `across +180 m`——**全在 40 m 宽的走廊之外**。`closedDays` **0/22**。
2. **末班车"世上没有"，不是"我们没抓"**：`pack.json` 的 `scopeNote`（L582）逐字写着——本包有市巴士均一运賃的来源，但 **"no sourced stop-to-stop running time, headway or first/last departure for any route"**；L263 同向。9 条腿**全是 walk**，合计 55 分钟，`fareIC/fareTicket` 全 `null`；`fares.priceableAsALeg = 0`。
3. ⇒ `export-guard` 提议的那句「**在 22:00 末班车前走到 X**」——**22:00 这个数在事实层里不存在。** 它会让 P1 第一次就把一个编出来的世界事实画到屏幕上，而那正是本项目存在的理由要防的事。

**⇒ P1 不引入截止压力。理由是"引入即造假"，不是"以后再做"。**

### 3.2 边界现在就定下来，所以它以后不能被偷偷引入

| # | 条件 | 检查方式 |
|---|---|---|
| **D-1** | 它引用的时刻是一个**有来源**的值，且挂在**走廊内的一个地点**上（或一条**触及走廊的线路**的有来源首/末班）：带 `source_url` + `verified_at` + `valueKind` | 事实层里能指到 |
| **D-2** | **每一个绑定中的截止时间，在它开始绑定的那一刻，屏幕上必须已经有一个备选**（`design-core` L557） | 不存在"逾期且无下一动作"的可达状态 |
| **D-3** | **导出物永不携带游戏内时钟**：攻略可以写"16:00 关门"（世界事实），**不得**写"你有 10 小时"（游戏规则） | 导出断言里，游戏时钟的任何量都不得出现 |
| **D-4** | 截止必须在**决策的那一刻可判读**：玩家选之前就能看见"现在去 X 就会错过 Y" | 决策点上屏幕含有两个分支的后果 |

**D-1 有一个一页纸就能解开的入口**：

> **走廊内唯一一个"我们没打开过它的官方页"的地点，是 `三菱ＵＦＪ銀行 京都支店`（`x=18.17 m`）。** `places.json` 自己的 `whyEmpty` 写着：`営業時間・ATM 稼働時間・住所は OSM に無く、銀行公式のページを本パックは開いていない`。
> **打开那一页 → 得到走廊内第一个有来源的时刻 → D-1 首次可满足。** 一件事、一个来源、一个 owner（`pack-curator` 抓、`fact-verifier` 核）。
> **在此之前，"时限下的抉择"这根支柱没有任何输入**（§6）。

### 3.3 我给这条命题本身划的界（判断）

- **不对称不是"游戏性 vs 可用性"的普遍张力**，它是**一个具体的等式**：`游戏内成本 = 现实成本`。**凡是让这个等式失效的东西都会让攻略变坏**；凡是没有让它失效的东西都不会。**所以"密度""发现摩擦"本身不危险**——危险的是给时间/金钱加折扣、加速、跳过，以及**把"你到过"当成"值已核"**。
- **允许**：截止、排队、走路慢、看不懂、猜错。**禁止**：买时间、快进、跳过等待、自动背书、"到过一次就永久更省时间"。
- **而"发现摩擦"是被保护的对象，不是风险**：摩擦越大，玩家在游戏里花的**现实时间**越多，导出的行程越接近他能承受的——**摩擦与余量同向，只有截止压力与余量反向。** 所以真正需要边界的只有截止压力一项，边界形状就是 D-1…D-4。

## 7 · 门洞级内容：每个门洞的四件事

**内容的单位是门洞与门后的内部空间**——每个门洞必须有四个字段，缺一个这门就是装饰：

```jsonc
{ "doorId": "D-N1",
  "anchor":   { "cellX": 18, "cellY": 24, "alongStreetM": 18, "approachJa": "街心向北 13 行" },
  "interior": { "template": "S", "depthM": 3.0, "modelled": true },   // 南侧: modelled=false
  "entry":    { "radiusTiles": 1.5, "requires": [] },                  // requires = 只增扁平标志
  "oneThing": { "kind": "readback", "factRef": "kyoto-shijo-bldg-mitsui" } }
```

- **`entry.requires` 是扁平、只增的标志集合**（不做脚本语言）。
- **`oneThing` 今天只允许两种 `kind`**：`readback`（读出事实层的值 + 来源）与 `placeholder`（南侧 3 扇，用户裁定）。**不允许 `cutscene` / `dialogue` / `reward`**——那些需要叙事层与资产，而它们会先于内容出现。
- **判据（能失败）**：**每个门洞的 `oneThing` 必须引用一个 `factRef`，且它在事实层里能解析到；解析不到就是装饰品。**（`geo-contract` 那条"留一个没读者字段比缺失更糟"的扫描规则的又一次应用。）

## 8 · R2 与可玩性判据（Lead ③）· 以及 SOW 该收什么（Lead ②）

### 8.1 我的判据**不以"门"的形式存在**，所以它不触发 R2

> **R2′ 要求每道门能报出"它实际拦下过什么"。可玩性判据拦下的东西是"一个脚本分不出来的构建"**——它拦不下任何东西，所以它**永远无法满足 R2′**。把 P1 判据造成一道门，就是造一道注定要被 R2′ 删掉的门。

**正确的形状是两层：**
1. **人的那一半 = 外部证据判据**（§1.8 的录屏 + 按键日志 + 两个固定问题），**不进 `run-gates.mjs`**，由 `fact-verifier` 判读。这与 SOW §3 已采纳的"产物式判据"是同一条纪律。
2. **机械的那一半 = 给已有断言器加断言**（R2′ 窄例外 1：给已有脚本加断言不算新增门）。三条，都挂 `check-viewer-page.mjs`：
   - `t=0` 时 `derived` 为空；
   - 首帧渲染出的真实名称集合 = 事实层里 `inSceneWindow` 的名称集合；
   - 驱动一次 `step()` 后至少一个显示量变化；走进任一锚点 1.5 格内后该锚点状态必翻转（不需要再按键）。
   **⇒ 新增 0 道门，`run-gates` 门数不变。**

**SOW 该写的例外（窄，一句话）**：
> **可玩性判据不被造成门。它以"外部证据判据"的形态存在（一次真人测试的产物），由 `fact-verifier` 判读；其中可机械化的部分挂到已有断言器上，不新增门。**

### 8.2 SOW 新增「玩法系统」一节的形状（由我定，因为归我）

**四小节，顺序即依赖顺序：**
1. **门洞级内容**（§7）——今天唯一不依赖缺失事实值就能做深的。
2. **目标引导四层**（§4）——L1 是 P1 本身；L2/L3/L4 依赖时钟与有来源时刻。
3. **整数时钟**（§5）——**入口条件是 D-1 可满足**，写成一条可勾选的前置。
4. **三支柱**（§6）——每根支柱写明"玩家做了什么决定、代价是什么、**今天的输入是哪几条有来源的值**"。

**这一节必须自带的三条纪律**：① 每一条判据都要能在现有 viewer 上测，测不了的写进"未决"；② 引导层不得持久化散文（§1.3 的可机械复核形式）；③ **三个集合（`derived`/`read`/`gloss`）永不加成同一个分数**（§1.7）。
