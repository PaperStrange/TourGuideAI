## 0. 设计核心（一句话）

> **让"在游戏里玩一遍"和"在现实里走一遍"成为同一件事的两次投影。**

不是"游戏里生成一份攻略让你去现实"，而是：**游戏世界本身就是真实世界的一个可玩切面**。
玩家在游戏里做的事、花的钱、走的路、看懂的招牌，全部是现实的。于是"游玩结束"自然产出攻略——**不需要一个"生成攻略"的功能**。

这一条同时解决三件事：游戏性（约束真实→决策有意义）、可信性（事实来自事实层→攻略可执行）、以及旧项目失败的根本原因（没有事实层，一切靠 LLM 编）。

## 1. 玩法：三个时间尺度

### 1.1 分钟内循环（30 秒–3 分钟）

```
在一条真实的街区里移动
  → 遇到看不懂的日文（招牌/菜单/告示/站牌）
  → 选择一种手段去弄懂：拍照留档 / 问 NPC / 从上下文猜 / 掏出手机（游戏内）查
  → 词汇表 +1，或猜错（后果是真实的：点错菜、上错车、排错队）
  → 决定下一个去处
```

**核心动词四个**：

| 动词 | 成本 | 收益 |
|---|---|---|
| **走** | 免费、慢 | 看见更多，触发随机遭遇 |
| **乘** | 花钱、快 | 省时间，但错过路上的东西 |
| **读/问** | 花时间 | 词汇与情报（= 攻略里的"可信度"） |
| **排** | 花时间 | 行程与预约（= 攻略的骨架） |

### 1.2 日内循环（15–40 分钟）

```
06:00 起（或玩家选择）→ 白天推进（时间以 tick 走）
  → 傍晚：疲劳与选择（我还想去一个地方，但会赶不上末班车）
  → 回住处 → 睡觉 → 结算：今天去了哪、花了多少、看懂了什么
```

**"睡觉"是存档点，也是攻略的导出边界。**（Stardew 的模型；实时钟表会与"导出攻略"这件事直接冲突）

**每天结束时自动长出一样东西**——一份**当日行程卡**：

```
Day 2 · 3月14日
  09:10  金阁寺        ✅ 你亲自到过  停留 55 分钟
  10:40  龙安寺        ✅ 你亲自到过
  12:00  蕎麦屋        ⚠️ 店休（周四）→ 备选：步行 6 分钟的 X
  14:20  市バス 59     ✅ 你坐过这一班，230 日元，12 分钟
```

**这是游戏的核心正反馈。** 玩家不是为了"拿攻略"才玩，而是**玩完就得到了一张记录自己今天干了什么的卡**，它恰好就是攻略。

### 1.3 全局循环（4–10 小时）

```
一座城市的若干天 → 离境 → 生成可执行攻略（真实世界用）
  → 去日本实际走一遍 → 回来把现实照片补进回忆录
  → 回忆录成为下一次旅行的动机与素材
```

## 2. 关键设计判断

### 2.1 游戏里的"发现"是真的

这是整个设计的支点。

> 玩家在游戏里找到一个隐秘小巷、发现某寺 16:30 关门、知道某店周四休息
> —— **这些全是真的**。
> 于是"攻略"不是游戏的外挂产物，而是**玩家真实获得的知识的记录**。

**推论**：游戏必须**奖励事实发现本身**，而不是把它当通关门禁。读者发现的每一条真实细节，既是游戏进展，也是攻略里的一条内容。

这条判断让"真实性"从负担变成核心玩法——**这是本项目与"AI 生成攻略"类产品的根本区别**。

### 2.2 语言障碍做成机制，而不是 UI 设置

> **玩家的词汇量 = 字体子集的大小。**

- 世界里出现真实日文。玩家**不能读**不是因为它被替换成"？？？"，而是因为**那些字形根本不在已加载的字体子集里**。
- 玩家学到一个词 → 字体子集 +1 个字形 → 街道上的招牌**真的变得可读**。
- 认知状态是**信念图**（`glyphId → 我的猜测`），而不是查表结果。游戏按"玩家以为的意思"行动。
- **判据**：把语言设置改成英文就能看懂所有场景内文字 → 那只是字符串表，不是机制。

这条把"字体子集化"这个技术负担（CJK 字体数 MB，首屏致命）**变成了机制的载体**。一举两得。

> **⚠️ 架构规则（必须遵守，否则机制当场失效）：**
> **两个消费者、两种产出方式，绝不同用一个文件。**
>
> | 消费者 | 产出方式 | 内容 | 代价 |
> |---|---|---|---|
> | **游戏世界渲染** | **构建期位图字形图集**（不是字体） | **仅玩家已学的字形** | 见下方实测理由 |
> | **导出文档（攻略）** | **构建期预烘字体超集**，一次做定 | 已学 ∪ **攻略所需的全部字形** | **57,412 B（492 字，已实测）** |
>
> 调研 §4E 原文写的是"子集 = 攻略所需 ∪ 已学"——**那条只适用于攻略**。若世界渲染也用这个并集，玩家一打开攻略就看见了自己**没学过**的字形，语言机制的核心（看不懂就是看不懂）立刻失效。
>
> **实测修正（2026-09，client-engineer）：世界文字不能用字体，必须用位图字形图集。** 原方案（`world.woff2` 真字体子集）要求**运行时按已学字形重新子集化**，而浏览器端子集器的实测成本是：
>
> | 项 | 字节 |
> |---|---|
> | harfbuzzjs WASM | **651,027 B** |
> | harfbuzzjs JS | 82,693 B |
> | 全量源字体（Noto Sans JP w400 全部 124 个 woff2 切片） | **2,793,024 B** |
> | **合计** | **≈3.4 MB** |
>
> **即：为产出一个 57 KB 的文件，要多下载 3.4 MB——而我们在同一台设备上还要求离线。** 因此：
> - **世界文字 = 位图字形图集**（12/24 px 两档，含墨团变体）；**运行时字体子集化从规格中删除**
> - **攻略字体 = 构建期预烘超集**，写入包内，**字节恒定**，可内联并纳入封面哈希
>
> **机制一字未改**：状态仍是同一个 `Set<GlyphId>`，仍是"一个文件被读两次"。
>
> **顺带退掉一笔成本**：原写"`guide.woff2` 在导出时单独请求一次，且导出必须能离线命中它"——因为攻略字形集是任何一次游玩并集的**超集**，构建期预烘即可，**导出时零请求、无离线缓存要求**。

### 2.3 三支柱机制（不做八个）

| 支柱 | 证明 | 为什么选它 |
|---|---|---|
| **验证与时限下的抉择** | Papers, Please | 规则有限且可读；规则**不充分**（单看都对，合起来矛盾）；**时间就是玩家的吞吐量**。玩家必须**能"做对却仍然失败"** |
| **解读（信念即状态）** | Heaven's Vault / Chants of Sennaar | 极便宜（一张 glyph→猜测 的 JSON 表），叙事回报高 |
| **路线与双资源规划** | 80 Days | 时间 + 金钱两个资源，结构风险低 |

**明确砍掉**：文化冲击计量条（无成功先例）、汇率套利（无先例且枯燥）、抽卡、任何"付费压缩时间"的机制（会摧毁游戏内成本＝现实成本这条等式）。

### 2.4 一天的单位是"门口"，不是"街区"

来自《如龙》神室町的公开复盘：**"隔一堵墙、上一段楼梯，就是完全不同的场景"**。

> **内容的单位是门洞与门后的内部空间。**
> 一条 40m×40m 的街 + 12 个可进入的内部，胜过 12 个街区。

这直接决定关卡与美术的投入方式：**做纵深，不做面积**。同样的作者劳动量，可进入地点数 ×4。

### 2.5 美术：买，不画

- 起步用 **CC0 模块化套件**（Kenney / KayKit）+ 每城一个**风格包**（调色板 + 招牌字体 + 6–10 个街区道具）。
- **若新增一座城市需要一个新的 tile 类型 → 那是设计缺陷，不是美术任务。**
- 手绘只买 **3–5 个地标建筑**，且只在循环跑通之后。
- **许可陷阱必须逐个查**：Cup Nooble *Sprout Lands* 与 shubibubi *Cozy People* 的免费档**仅限非商业**；CraftPix **禁止**用于 AI 训练/参考；FLUX.1 [dev] 禁止商业用途；LPC 的 CC BY-SA 会**传染**到我们的 tileset。

> **⚠️ 成本结构修正（我此前误判，专家红队指出）：**
> 第一城"买素材"确实是 **$27.94–33.94、0 绘画小时**——但**那不是账单**。真正的账单是：
> | 项目 | 工时 |
> |---|---|
> | **招牌 + 字形管线** | **60–90 h**（全项目最贵的单块） |
> | 其余系统工时（tile 管线 / autotile 映射 / 场景装配 等） | 72–120 h |
> | **合计自建** | **132–210 h** |
>
> **三项必须记住的隐性成本：**
> 1. **LimeZu 的 autotile 元数据只给 Godot 与 GameMaker，Tiled/Phaser 消费不了。** 买来的"模块化套件"**不自带**我们需要的 autotile 映射——这 8–16 h 是**买不到的自建成本**，不能排进"买来即用"。
> 2. **Unity 资产店的 The Japan Collection（免费版）在 Phaser/浏览器构建里视同不可用**（Unity EULA + "Extension Asset" 授权范围）。**不要把它当日本城市素材的免费起点。**
> 3. **GameDev Market 的 Osaka / Dotonbori 价格与条款是 UNVERIFIED（403 抓不到）→ 不得进预算**，必须人工开页面确认。
>
> **"模糊母版生成"（未学字形用模糊墨团渲染）是整个规格里唯一没有现成实现的一步**：`pyftsubset` 只裁剪不降质，需要栅格化→模糊→矢量化，**2–3 天未知数、可能翻倍**。它同时是"感知差异最大、且通用素材包完全不覆盖"的那一项，**省不掉也没人卖**。
> **被迫降级方案（机制一字不改）**：改用**预渲染汉字图集**（委托 $150–400 或 ~20 h 自绘，300 字形上限，墨团 = 同图集 22% 墨量版）——**直接删掉整条字体工程**。

> **两条机械门的提议（我采纳）**：
> - **SK-1 `validate-city-kit.mjs`**：每格 tileId ∈ hash 锁定的 `tiles.json`、`localProps ≤10`、调色 ramp 合法。失败 = **真需要新 tile 类型 = 设计缺陷**。
> - **SK-2 `MASK_KIT=1` 构建**：**关掉全部装饰后仍须洪泛可达 12 个门、零未贴图格**。失败 = **风格包在承重 = 设计缺陷**。半天的脚本。
> - 建议把 **SK-2 定为阶段 5「第二座城市」的验收门槛**——它是"新城市只需风格包"这条规则的**唯一机械证明**。
> - 建议把**招牌普查脚本（输出字形数与笔画数）列为阶段 3 的构建产物**：§2.2 里 30%/80% 的字形数**必须是普查结果，不能是任何人拍的数**。

## 3. 真实性：把"可信"做成可机械检查的东西

**三条不可协商**（已写入 `.dsh/skills/tourguide-fact-integrity/SKILL.md`）：

1. **没有来源，就没有地点。** 每个事实字段必须带 `source_url` + `verified_at`，否则该地点不进入游戏、更不进入攻略。
2. **drop, don't correct。** 校验拒绝的内容一律**丢弃或降级为朴素模板**，绝不补一个"看起来合理"的值。
3. **付费不得改变时间/金钱账本。** 一旦能买时间，游戏内成本 ≠ 现实成本，导出的攻略就不再可执行。

**新鲜度分三层**：静态（坐标/地址，年检）／半静态（营业时间/票价，季度复核）／动态（临时休馆，运行时查询或标"出发前请确认"）。

**攻略里每条都带溯源**：`source_url` + `verified_at` + **一个可信度标记，且这个标记由玩家的行为派生**：

| 玩家做了什么 | 攻略里的标记 |
|---|---|
| 亲自到过 | ✅ 已验证（你亲自确认过） |
| 在游戏里读过来源 | 📖 已核实 |
| 只见过传闻 | ⚠️ 待确认 |

**这让"游玩"与"可信度"变成同一个变量。** 玩得越认真，攻略越可信——不是靠我们声明，而是靠玩家自己走过。

## 4. 世界模型四层（Appendix B 的机制在这里落地）

```
① FACT     city-packs/<city>/{pack,places,transit}.json   每个事实带溯源
              ↑ 只读
② SIM      Phaser 4.2.1：场景 / 整数 tick 时钟 / 玩家状态 / 事件
              ↓ 玩家动作 → 命令日志
③ ITIN     确定性 TS：玩家动作 → 结构化 GuideDoc（无 LLM）
              ↓ 冻结的 GuideDoc（只读）
④ NARR     LLM 只吃冻结的 GuideDoc，只吐文本
              输出 schema 里【没有任何字段能装下事实】
```

**玩家状态**（决定攻略长什么样）：

```ts
{
  pos, tick, day,
  money,                 // 现实预算
  fatigue,               // 软约束：累 → 能读懂的更少（不是血条，不会死）
  derived: Set<FactId>,  // 你亲自到过  → 攻略 ✅
  read:    Set<FactId>,  // 你读过来源  → 攻略 📖
  gloss:   Map<GlyphId, Guess>  // 信念图   → 能读懂哪些招牌
}
```

**关键**：`derived` / `read` / `gloss` 三个集合**同时是游戏进度、存档内容、和攻略的可信度字段**。一个数据结构，三处用途——这是本项目最省力的设计。

## 5. 攻略即产品界面

攻略不是"一个功能"，是**产品的可见交付物**（也是唯一能让玩家真的去日本的东西）：

- **必须是确定性的**：同样的游玩 → 同样的攻略。可复现是能调试、能修 bug 的前提。
- **必须可打印 / 可离线**：出门在外没有网。
- **每条都带**：来源、验证日期、可信度标记、Plan B、缓冲时间。
- **交通**：策展的常用路线 + **深链**到 Google Maps / 乘换案内。**不做全网算路**——那是另一个产品的工作量。
- **语言卡**：把这个玩家**真的学过**的词做成小卡片（不是通用旅游会话手册）。

## 6. 架构边界（机械可检查）

```
src/
  app/         React 18 shell：路由 / 攻略页 / 回忆录页 / 设置
  game/        Phaser 4.2.1，单个 canvas 岛；独占自己的 RAF
  facts/       ★只会读 city-packs/**，【不 import 任何 LLM 客户端】
  narrative/   ★只会接受冻结的 GuideDoc，【不 import facts 的写接口】
  compose/     唯一允许同时 import facts 与 narrative 的模块
  guide/       导出（确定性）
  memoir/      照片回流
```

**两条 CI 级约束**（Appendix B 七层机制的前两层）：
- `facts/**` 不得 import LLM 客户端 —— 用 ESLint 依赖规则强制
- `narrative/**` 的输出 schema 里**不允许存在能装下地点/时间/价格的字段** —— 用 zod discriminated union + 运行时校验

**构建期资产管线（build-time），不是"后端"。** 地图、字形图集、tilemap 与攻略字体**全部在构建期烘焙成随游戏分发的文件**——运行时**零 API 调用**（见下方 LLM 定位）。旧项目的两个代理保留为**策展期工具**（`openai.js` 把 key 从浏览器 bundle 拿走；`googlemaps.js` 帮人更快打开来源页），由 owner 在策展时运行，**永不随游戏分发、永不进运行时**。

> **⚠️ 架构勘误（2026-09，backend-architect 指出；本句此前写的是"后端：复用旧项目骨架"）：**
> 原文在一份**自我声明"零 API 调用"**的文档里继承了"Express + 限流 + 日志 + 缓存 + vault"这套**以服务请求为目的**的基础设施，自相矛盾。
> 平台横评之后这条矛盾变成了可证明的：**没有任何供应商被许可在运行时给我们瓦片**（Google §4.2/§5.2、Mapbox「may not be preloaded, bundled」、MapTiler「prohibited to manipulate or modify」、Stadia ≤100 MB/7 天），所以地图**必然是构建期资产**。
> **地图一离开服务器，服务器剩下的运行时职责就没有了。** 保留"后端"这个词的代价不是清洁度，而是它会持续诱惑出账号/同步/多人——**而这三项都在 §7 的拒收清单上**。
> 处置：**"后端"改为"构建期资产管线"**；`server/` 目录**不删、但不给它角色**（见 §8.5）。

**两个旧资产是"危险的顺手"**：`server/routes/googlemaps.js` 是仓库最好的代码，**因此最容易被拿来当事实源**——它的结果不经人工打开来源就进 `places.json`，恰恰是事实层要防的那件事。1 小时的响应缓存也必须重写语义（两个玩家拿到逐字相同的内容是 bug）。

**LLM 定位：默认关闭。** 游戏必须在**零 API 调用**下完整可玩——这既是"LLM 只是调味料"的机械证明，也是唯一可行的离线与成本方案。实测：预烘焙 500 个任务 ≈ **$1.03**，而 2500 token 的任务实时生成要 **9.5–15.3 秒**（不是实时预算）。

## 7. 分阶段规划（按风险排序，不按功能排序）

按调研得出的分布：**能在几个月做完的游戏几乎没有美术生产；凡是有"世界"的都花了 3–9 年。** 本项目的"世界"就是那个 3 年量级的东西——所以规划的核心不是压缩，而是**让"该不该继续"在每个阶段都便宜可测**。

### 阶段 0 — 7 日证伪（零代码）★最高优先级

**风险最高的假设**：*玩家会真的导出攻略、并在现实旅行中使用它。* 这是全部调研里**唯一没有任何成功先例**的假设，也是**上游假设**——不成立则事实层毫无意义、2.5D 精细度只是装饰，正确工程量差一个数量级。

**它必须用实物而不是研究来回答**：
- 第 1 天：手工策展**一个真实街区**的 30 个地点（每字段带来源 + 验证日期，**来源必须真的打开读过**）
- 第 2 天：**不含 LLM、不含游戏**，纯模板生成一份可打印攻略
- 第 3 天：一屏"游戏观感"假图（只为让受试者理解形态，不是原型）
- 第 4–5 天：交给 **3 个真的要去那里旅行的人**
- 第 6–7 天：复盘并决定

**通过标准（写死，避免自我说服）**：3 人中 ≥2 人用它做出了"否则不会做"的决定，且 ≥1 人主动索要另一座城市的同类文档。

**同时必须记录**：**每个地点的策展耗时**。> 20 分钟/地点 → 150 地点的城市包对 1 人不可行。**这个失败模式在有人照着错误营业时间白跑一趟之前是看不见的。**

**不通过怎么办**：攻略被读但没被用 → "导出攻略"是功能不是产品，应按他们实际做的事重新定范围（按证据看很可能是**回忆录**那条线）。**两种情况下都不要开始写引擎代码。**

### 阶段 1 — 事实地基（3 周）
1 座城市的数据包 + schema + `validate-city-pack.mjs` 进 CI。**无 LLM、无渲染。**

### 阶段 2 — 技术骨架（3 周）
Vite + React 18 + Phaser 4.2.1 + 单一事件总线 + 整数 tick 时钟 + IndexedDB 存档 + 命令日志回放 + 调试覆盖层。

### 阶段 3 — 垂直切片（6 周）★第一个可玩里程碑
**一个区、三天、8–12 个可进入地点、一个机制、攻略导出、回忆录 v1。无 AI。**

| # | 决断 | 内容 | 证据强度 |
|---|---|---|---|
| **①** | **范围分层：2 km 派生 / 1 街区手作** | **2 km 走廊 = 派生几何**（攻略路线 + 可走网格，成本近零，工具链一次性投入）；**Gate 1 手作美术 = 一个 `40×40` 街区**（约 26 个店面模块，含 12 扇门） | **三线独立收敛**：L3 算出手作立面 **2,600 px vs 625 px（4×）**；L4 独立算出 2 km 按同密度 = **1,300 店面模块（50×）** 且**走完需 1.98 个游戏日**（一日最多走 1,008 m），与时间系统矛盾；**L2 证明工具链一次投入、两范围共用** |

| **③** | **`building:levels` 缺口 → PLATEAU 京都市** | OSM 实测有值率仅 **8.6%**（分区更糟：烏丸 25% / 河原町 7% / **祇園 1%**）。**PLATEAU 京都市**（G空間情報センター，2025/2023/2022 年度）含 **建築物 LOD0/1/2.0/3.3** 与**道路モデル（MVT）**；数据集描述原文「**商用利用も含め、どなたでも無償で自由にご利用いただけます**」 | 我实测 + L2 独立核实 ⚠️ **但 `PLATEAU Site Policy` 逐条原文未取到（官网 JS 壳）——发布前必须补取** |

**另两条由 L2 提出、我核实后采纳，且它们动的是事实层：**

| # | 新增 | 内容 |
|---|---|---|
| **④** | **`valueKind` 维度** | 现有三态（`✅ 亲自到过` / `📖 读过来源` / `⚠️ 待确认`）只描述**"玩家做了什么"**，不描述**"这个数本身怎么来的"**。新增 `valueKind: observed \| licenced \| abstract`，**`abstract`（PLATEAU LOD1 抽象高度）与 `licenced`（道路宽度授权模板）禁止出现在攻略的"已验证"栏位**。否则**"亲自到过"会给一个抽象高度背书**——两种不同的可信度混在一列里 |
| **⑤** | **`worldGrid` 常量写死** | `{ wTiles: 2000, hTiles: 40, blockSize: 40 }` 进 CI。**"1 格 = 1 m"与"40×40 格 = 一个街区"被混用会在第一次做地图时炸掉**——2 km 是 **80,000 格 = 50 个街区并排**，不是一张 1280×1280 的 tilemap |

**两条口径必须写死在规格里**（否则普查脚本会产出与规格"矛盾"的数字，然后有人会以为规格错了）：

- **字形数**：`450` 是**按招牌面积加权的 80% 覆盖率**；L2 实测 2 km 段**按串计数**是 **1,566 个不同 CJK 字形 / 4,508 个唯一名串**。**两者不矛盾，是两个口径**——普查脚本必须同时输出两个
- **地面层上屏必须索引色**：2 km × 32 px = **8,192 万像素**，RGBA 原始 = **312.5 MB 显存**（L4 与 L2 各自独立算出同一结论）

**L2 指出的成本缺口**（我认）：设计 §2.5 的"买，不画"在**几何层不成立**——买来的是词表（tile/props），**派生的是几何（轮廓/道路/水系）**，两者不在同一采购清单。**派生几何的工具链约 100–170 h 一次性，在设计成本表里没有对应行，量级接近招牌管线的一半。**

### 8.2.2 地面层切分与导出契约（用户裁定 2026-09-29）

**① 地面层 = 16 块**

| 项 | 值 |
|---|---|
| 走廊地面像素 | **64,000 × 1,280 px** |
| **分块** | **16 块，每块 4,000 × 1,280 px**（= **125 × 40 格**；`2000 ÷ 16 = 125` 整除） |
| 单张纹理上限 | 4096 × 4096 px → **每块放得下 ✅** |
| 索引色内存（8 bit，16 块合计） | **78.1 MiB**（对比 RGBA 单张 **312.5 MiB**，不可能） |
| 已知浪费 | 纹理**纵向利用率仅 31.3%**（4096 高只用 1,280）。第一版接受；要省可纵向堆 3 块变 6 块 |

> 这条**解掉 `contract-geo-pipeline.md` GAP-1 的一半**（切法已定），并**修掉附录 §1.3 那句"只用 40²"**——那是指**一个手作街区**，与走廊的 **80,000 格**是两个不同的量。

**② 导出契约：接受结构，但必须做多语言**（用户明确要求：**不能只用少数几种语言当测试用例**）

`assert-export-boundary.mjs` 的属性结构（`data-tgf` / `data-prov` / `data-entity` / `data-time` / `data-ui-strings`）**接受**。但多语言要求成立，且比它看起来重要：

| 文字系统 | 为何日语的规则不通用 |
|---|---|
| **日语** | 无词边界、无大小写 → 已实测误报 **145.6 / 1000 汉字**，故必须声明式 |
| **中文** | 同样无词边界；**简繁字形不同** → 允许清单必须按**字形**而非按词 |
| **韩语** | 有空格，但**助词黏着**（`서울역` / `서울역은`）→ 按字符串匹配会漏 |
| **泰语 / 老挝语** | **词间无空格**，最难 → 必须完全依赖声明 |
| **拉丁系** | 有词边界，但**专名靠大小写** → 句首会误判 |

**因此规则是「声明式为主、字形规则为辅」，且每种语言的规则是独立可插拔表**，不得把日语正则当通用规则。

**待做**：测试语料**至少覆盖 5 种文字系统**（现仅日语）；"按字形类判专名"降级为**每语言可选、默认关闭**的扫描。

### 8.4 D2 的实质差异（重写版，用户反馈「没看懂好坏差异」）

三个选项的差别**不在技术，在"玩家在大阪街头那一刻会发生什么"**：

| | 玩家在京都站想去金阁寺时看到 | 现实里照做会怎样 | 代价 |
|---|---|---|---|
| **自算** | 游戏实时算出一条换乘方案，含班次与票价 | 能用，但**可能与现实不符**（时刻表变动、临时改点），而玩家无从分辨 | 需要全网算路 + 多个换乘数据源，**许可逐源确认**，工作量等于另一个产品 |
| **全深链** | 一句"点这里查路线"（指向 Google Maps 之类） | **需要网络**。在京都站地下或祇園小巷里没信号 → **攻略当场失效** | 零算路成本；但直接压垮核心承诺「不用做攻略」 |
| **混合（我认为唯一可行）** | 常用路线给出**人策展的**具体乘车段（线路名、站台、票价、末班车）；冷门区间给深链并**加注"出发前确认"**；实在查不到的记为**显式缺口**「本作不提供该信息，请预留 30 分钟缓冲」 | 主线不依赖网络，冷门有诚实退路 | 需要人工策展常用路线（策展工时的一部分） |

**决策点其实是一个问题：你接受"部分区间需要联网看链接"吗？** 接受 → 混合；不接受 → 必须自算（工作量翻倍且许可复杂）。

3. **实测到一个新事实**：客户端里同时存在两套 baseURL 写法（`api.js` 指向 3001、`googleMapsApi.js`/`index.js` 指向 3000）外加一个 `useServerProxy` 开关——说明"走不走后端"曾被做成可选项，两套不是同一次改动的产物。且 `openaiApi.js` 里 `REACT_APP_OPENAI_API_KEY` 会被打进浏览器 bundle（**必须避免的写法**）。

**我的建议（不含决策）**：**不现在删，而是现在"降低它的地位"** —— 阶段 0 与 Gate 1 期间一行不改；在允许清单里限定 `server/` 只能保留两个"可弃代理"、其余目录不得新增文件；**Gate 1 之后再依事实判断搬移、重写还是不要**。理由：删掉一个不被 import 的目录不会让产品更接近成立，而"清理"是最容易被包装成进展的失控形式。

**在用户据此批复之前，不对 `server/` 做任何改动。**

## 9. 这份设计怎么算成立


| 判据 | 怎么测 |
|---|---|
| 游戏本身好玩 | 阶段 3 门槛 1（不知情的人玩了想继续） |
| 攻略现实可用 | 阶段 3 门槛 2（另一个真人照着走通） |
| LLM 只是调味料 | **关掉所有 API 调用，游戏仍完整可玩** |
| 事实层真的在管用 | `validate-city-pack.mjs` 在 CI 里拦住任何无溯源的事实 |
| 成本受控 | 每会话 LLM 花费有硬上限；预烘焙包可离线 |
| 没有范围膨胀 | 任何与"玩→导出→旅行→回忆录"无关的功能，一律拒收 |

## 10. 我认为最可能出错的地方（自陈）

1. **美术量被低估。** 调研里"有世界的游戏花 3–9 年"是硬数据。缓解手段是把"世界"的定义**主动缩小**到"一个区 + 深处"（§2.4），但这条能否撑住 3–5 座城市，**我没有证据**。
2. **策展是隐形工时黑洞。** 每个地点的来源要真的打开读、季度复核。20 分钟/地点这条线如果被突破，整个事实层战略要重估。
3. **语言机制可能做出来不好玩。** 它是本设计里最新颖的一块，也最没有先例（Heaven's Vault 的成功是单人叙事游戏，不是开放街区）。
4. **"玩一遍 = 一份攻略"的映射可能过于理想。** 玩家在游戏里的最优解，未必是现实里舒服的行程（游戏里赶时间是乐趣，现实里赶时间是灾难）。**这一条需要阶段 3 用真人验证，可能需要一个"现实节奏"校正层。**

   **⚠️ 已升级为设计的核心待验证命题（专家红队指出，我认）：** 上面这句话比它看起来更严重——那个"节奏校正层"**就是本设计声称不需要的"生成攻略"步骤**。所以主张必须精确化为：
   > **游玩产出一份草稿，其唯一需要的后处理是节奏。**
   这比"玩一遍就是攻略"弱，但**可测、可证伪，且是真正承重的那一条**。

   **零工程验证（并入阶段 0 的 7 天，约 1 小时）：** 给每位测试者**两份**同街区的模板日程——
   - `G` 贪心版：最多地点、最紧换乘、**按游戏奖励的形状造**
   - `S` 缓版：同地点减两处、+30% 缓冲、晚起

   走哪份自选，逐项记录"做到了 / 想做没做"。**判读**：≥2/3 人中途放弃 `G`，或 ≥3 项"想做没做" → 节奏校正层为必需，主张降级；`G` 撑住了街头接触 → 本设计成立，专家判断有误。

   **另一处必查（游戏内无"安全迟到"状态）：** 错过末班车且屏幕上没有 Plan B，等于游戏制造了攻略本该防止的那个结果。**任何能把末班车变成"可恢复失败"的设计，都是承重设计而不是润色。**
