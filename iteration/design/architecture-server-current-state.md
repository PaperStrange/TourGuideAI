## 0. 先更正一个被我自己报错的数字

我在清单里说过 `server/` 有 **4,053 个 `.js` / 475,524 行**。**那是错的。**

| 组成 | 文件 | 行数 | 性质 |

## 4. 活跃度：客户端怎么找后端（实测 22 处引用）

**这是一个真发现：仓库里同时存在两套指向后端的写法。**

| 写法 | 出现位置 | 指向 |
|---|---|---|
| `REACT_APP_API_URL \|\| 'http://localhost:3001/api'` | `api.js:7` | **3001**（后端端口） |
| `REACT_APP_API_URL \|\| 'http://localhost:3000/api'` | `googleMapsApi.js:21`、`index.js:20` | **3000**（CRA 开发服务器端口） |
| `REACT_APP_USE_SERVER_PROXY === 'true'` | `googleMapsApi.js:22` | **一个开关，决定走不走服务端代理** |

**读数**：默认值不一致（3000 vs 3001）说明**这两套不是同一次改动留下的**；`useServerProxy` 存在则说明"走不走后端"曾被做成可选项。这与旧调研的判断一致（真实 LLM 路径是浏览器直连）。

**同时确认两件事**：
- **根 `package.json` 没有 `proxy` 字段** —— CRA 未配代理
- `scripts.dev` = `concurrently "npm run start"(3000) "npm run server"(3001)` —— 开发时两个进程都起

**一处安全问题（实测）**：`openaiApi.js:66-67` 直接读 `process.env.REACT_APP_OPENAI_API_KEY`。**`REACT_APP_*` 会被打进浏览器 bundle** —— 这是把 API key 送到客户端的写法。重启项目必须避免。

## 6. 我的建议（不含决策）

**我的立场：不建议现在删，但建议现在"降低它的地位"。**

理由分三层：

**① 8,569 行里约 1,400 行明确属于已废的 beta 产品**（`auth` 506 + `inviteCodes` 234 + `admin` 177 + `emails` 276 + `emailService` 325）。这部分**不服务任何循环腿**（`walk/ride/read/plan/export/memoir`），按范围纪律应当拒收——**但它们的存在不构成"现在必须动手"的理由**。

**② 剩下约 630 行（两个代理）有具体价值**：`openai.js` 解决"key 不进 bundle"这个真问题；`googlemaps.js` 只在策展期帮人更快打开来源。**而这两件事都可以由约 200 行的 serverless 函数完成**——所以"保留骨架"的价值确实不高。

**③ 但删除本身不是收益。** 删掉一个不被 import 的目录**不会让产品更接近成立**，而它会消耗一次改动窗口与我的复核精力。真正有价值的是**阻止它长出新的东西**——即：**不预设通用后端**。

**所以我建议的处置**：
1. **阶段 0 与 Gate 1 期间：不动 `server/`**，一行都不改（阶段 0 是零代码证伪，碰它没有收益）
2. **在 §0/§1 的"允许清单"里明确 `server/` 的角色**：只允许存在两个"可弃代理"，其余目录**不得新增文件**
3. **Gate 1 之后**，等 `openai.js`/`googlemaps.js` 的真实复用需求出现时，**再决定是搬进新架构、还是重写为 serverless、还是连它们一起不要**——那时判断依据是事实而非推断
4. **不论何时删，都必须先满足你的要求**：本文档就是那份"架构设计方式 + 改造理由"；**在你据此批复之前，我不动它**

**明确否掉的一种做法**：以"清理"为名现在就删。历史基准率告诉我们，这个项目死于**范围失控与工具链膨胀**，而"清理"是最容易被包装成进展的失控形式。
