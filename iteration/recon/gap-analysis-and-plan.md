## 0. 一句话结论

旧项目**不是"代码烂"**，而是**"工程过程吃掉了产品"**：79% 的 `src/` 代码在做一个与旅游无关的 beta/问卷/UX 审计子系统，而真正的旅游功能不可达、地图是假的、后端在启动时就因缺依赖而死。**但它有约 4,500 行真正值钱的基础设施可以搬走。**

新目标比旧项目难一个量级，因为它多了一条旧项目完全没有的要求：**输出必须在现实世界可执行**。这条要求推翻了旧架构最核心的假设——"内容由 LLM 生成、对错由用户自己核对"。因此：

> **本项目的最高设计原则：游戏世界本身即事实。**
> 玩家在游戏里走过的地点、时间、交通、费用，就是真实世界的地点、时间、交通、费用。
> 于是"在游戏里玩一遍"**自动等于**"生成一份可执行攻略"，游戏性与现实性不再是对立的两件事，而是同一件事的两次投影。

### 1.3 旧项目"bug 太多"的五个结构性真因

这五条比任何单个 bug 都重要，因为它们决定了新项目**必须换掉的做事方式**：

1. **安全网挂在错误的模块上。**
   `src/api/openaiApi.js` / `src/api/googleMapsApi.js` 不是文档宣称的"再导出兼容层"，而是**两份完整独立的分支实现**（348 / 639 行），且 `openaiApi.js:9` 的 `export *` 被 8 处本地同名导出**完全遮蔽**，属于装饰性代码。关键后果：**7 个 API 测试里 5 个测的是死分支，而应用实际运行 `src/core/api/*`**。
   → 所以"测试通过了"这个信号在这个仓库里**无效**。这是"越修 bug 越多"的第一大来源。

2. **根本没有服务端路线生成后端。**
   `server/clients/openaiClient.js`、`googleMapsClient.js` 是**硬编码巴黎假数据的 mock**（源码注释自认）；`routeGenerationService.js` / `routeManagementService.js` / `RouteModel.js` **只被测试引用**，`server.js` 完全没有挂载 `/api/routes`。而客户的 `RouteGenerationService` 却在调 `/api/routes/analyze-intent`、`/generate`、`/surprise`、`/optimize` —— **五个端点全部 404**。玩家看到的是"Error analyzing query"。

3. **真实 LLM 路径把 API Key 打包进了浏览器。**
   客户端代理路径的 `config` 里**没有 `apiBaseUrl` 键**，所以请求打到 `http://localhost:3000/openai/...`（什么都不在那儿），且代理默认关闭；于是默认走直连分支，`REACT_APP_OPENAI_API_KEY` 被 CRA 在构建时**内联进 JS bundle**。这直接推翻 `ARCHITECTURE.md:202` 的"API key 永不暴露给客户端"。
   → 对一个要分发的游戏客户端，这是必然的预算流失口。

4. **旅游产品本身不可达，地图是虚构的。**
   `/chat`、`/map`、`/profile` 全部挂在 `NavGuard role=[BETA_TESTER]` 后面（需要内测邀请码）；`src/features/travel-planning/`（10 文件 / 1,794 行，全仓库最完整的 UI）**没有任何路由指向它**；`MapPage.js` 610 行里，所有 marker 坐标是 `38.8977 + (Math.random()-0.5)*0.02`（华盛顿国家广场附近的**随机抖动**），交通方式从 `['walk','taxi','bus',...]` 随机取，时长/距离/推荐理由全是 `Math.random()`。

5. **修 bug 的系统比产品还大。**
   67% 的代码是"测试内测用户的工具"。这是**过程幸存者偏差**的教科书案例：项目把"我们做了多少 QA 流程"当成了进度，而底层产品从未真正成立——所以流程再完善也无法产生可用产品。`.cursor/.todos` 675 行、`.project` 445 行、`.milestones` 202 行，全部标记 `[X] COMPLETED`，其中"离线能力"、"重试策略"、"安全密钥管理"三条被代码直接证伪。

## 2. 目标状态定义（把用户的话翻译成工程约束）

### 2.1 产品定义

不是"一个旅游游戏"，而是**三件套闭环**：

```
  ① 在游戏里预演（2.5D 步行探索 + 行程决策 + NPC/文化互动）
        │  玩家的每一次选择都是一次真实的行程决策
        ▼
  ② 一键导出「可执行攻略」（现实世界照着走）
        │  行程表 / 交通 / 时间 / 费用 / 语言卡 / Plan B
        ▼
  ③ 去日本实际执行（一个人或和朋友）
        │  回来把现实打卡照片上传
        ▼
  ④ 生成「旅游回忆录 / 相册」（虚拟体验 + 现实体验合订）
        └────────────► 回到 ①（下一次旅行的素材与偏好）
```

**核心卖点（用户原话）**：让玩家在不额外做攻略、不找地陪、不因文化差异害怕的情况下，轻松复刻游戏里的路线。

**这带来三条不可协商的硬约束**：

| # | 约束 | 含义 |
|---|---|---|
| C1 | **事实性** | 游戏中出现的地点、地址、营业时间、票价、交通方式与耗时，必须来自真实数据源，且带验证时间戳。LLM 只能写"叙事包装"，绝不能写事实。 |
| C2 | **可执行性** | 导出的攻略要能被人拿在手上执行：分流时段、备选方案、预约提示、语言卡、IC 卡/车票说明。 |
| C3 | **双向性** | 回忆录要能接收现实照片（EXIF 时间/GPS），并把它与游戏内的同一天/同一地点**对齐**。 |
| C4 | **游戏优先** | 游戏是**主产品**，攻略是游玩后的自然产出。若玩家"为了拿攻略"才被迫玩，产品就失败了（见 §2.3）。 |

### 2.3 游戏优先（Game-First）原则 —— 对 v1 框架的修正

**v1 草案的错误**：把游戏写成了"攻略的模拟器"，攻略是目的、游戏是手段。这个框架会做出一个"必须忍受着玩完才能拿到攻略"的产品——**没有人会玩，于是也没有攻略市场**。

**正确框架**：

> **游戏本身就是消费价值（代入感 + 目标引导 + 收集欲）。**
> **攻略不是它的目的，而是它"不可避免的副产品"。**
> 玩家在游戏里变强、解锁、收集、推进剧情 —— 顺手得到了一份真的能用的行程。
> 这份行程让他真的去日本 —— 而现实旅行又给游戏供给新的收集品、新照片、新剧情。

于是三件事形成正循环，而不是相互妥协：

| 层 | 玩家感知 | 设计职责 |
|---|---|---|
| **代入感**（Immersion） | "我真的在东京街头找那家店" | 2.5D 场景、昼夜与营业窗口、语言障碍、NPC 互动、失败与意外（走错站、店休） |
| **目标引导**（Progression） | "下一站去哪、为什么去、我还差什么" | 任务链 / 图鉴 / 收集 / 章节解锁 —— **目标系统的骨架由现实地理决定**（见下） |
| **变现与周边**（Monetization） | "我想要那个东西" | 实体化收集品、纪念品、相册印品、城市扩展包（见下） |

#### 2.3.1 目标引导：让"现实地图"成为游戏的关卡图

这是把"游戏乐趣"和"攻略可用性"焊死在同一个结构上的关键设计：

```
游戏内的推进单元 = 现实中的一个地点/一条街区
       ↓
每个地点有：收集目标（图鉴条目/徽章/纪念物）+ 故事碎片 + 现实约束（营业时间/交通）
       ↓
玩家为了"在游戏里推进"，必须理解并遵守那个地点的现实约束
       ↓
于是：玩家的游玩轨迹 天然 就是一份遵守现实约束的行程表
```

**推论（产品纪律）**：**每新增一个游戏关卡，就等于新增一个已经策展过的事实地点。** 关卡设计与事实数据维护是同一件事，不会分叉。这正是旧项目缺的那条"内容即数据"的主线。

#### 2.3.2 变现机制（与真实性不冲突的部分）

| 机制 | 形态 | 为什么成立 | 红旗 |
|---|---|---|---|
| **图鉴 / 徽章收集** | 每地点一枚"旅行印记"，集齐一座城市解锁章节 | 收集欲是最稳的目标引导；同时天然生成"我去了哪"的清单 | 不可用抽卡随机化真实地点 |
| **实体化收集品** | 游戏内收集的印记 → 可兑换/购买实体周边（印章本、城市徽章、明信片、印制相册） | **"我在游戏里拿到了，现实里也能拥有"是把情感投射变现最自然的形式**；且它直接激励真实出行 | 需解决制造/物流/库存，属运营而非开发 |
| **回忆录印品** | 相册一键印成实体书 | 用户已投入真实旅行的情感成本，付费意愿最高 | 印刷质量与物流体验是口碑风险 |
| **城市扩展包** | 第 2、3… 座城市作为内容包 | 内容边际成本可测（见 §5 阶段 7），是最诚实的付费点 | 不能把"第一座城市"切碎卖 |
| **外观 / 装扮** | 角色服装、相机外观、相册主题 | 纯装饰、不破坏真实性 | — |
| **攻略增值** | 高级攻略：离线包、多人协同、预约提醒 | 真实有用 | 不能把"能用的攻略"锁在付费后，否则 C4 崩 |
| ~~付费加速 / 跳过排队 / 快速传送~~ | **禁止** | **游戏内的时间与费用成本必须等于现实成本。** 一旦可付费压缩，游玩轨迹就不再等于可执行行程，整个 C1/C2 基础崩塌 | 🔴 硬红线 |

**变现原则一句话**：**只卖"收藏与表达"，不卖"时间与捷径"。** 前者放大真实性，后者摧毁真实性。

#### 2.3.3 这对规划的直接影响

1. **阶段 3 的验收标准必须补一条"好不好玩"**（见 §5 阶段 3）——否则会做出一个逻辑正确但没人想玩的东西。
2. **新增阶段 6.5：收集与收集品系统**（见 §5）——它不是"后期润色"，而是目标引导的载体，必须在单城闭环之后、多人之前做。
3. **美术预算要重新分配**：既然游戏是主产品，场景观感与角色表现直接决定留存，不能再只按"攻略工具"的标准压美术成本。
4. **§7 纪律第 4 条的度量需要补充**：不能只问"能不能玩 30 分钟"，还要问"**玩完想不想再来一次、想不想真的去**"。

### 2.2 为什么是"重写"而不是"修旧"

不是因为旧代码不可修（它只是缺依赖），而是因为**三个致命假设已经不成立**：

| 旧假设 | 新现实 |
|---|---|
| 内容是"建议"，用户自己核对 | 内容是**指令**，用户照着执行。幻觉从"体验瑕疵"升级为"把人困在不会说日语的城市" |
| Google Maps 是地图 | Google Maps 是**事实来源**，但**不能作为游戏渲染层**（ToS 禁止离线缓存瓦片，且它是 2D 滑图组件，没有相机/深度/精灵系统） |
| 世界无限大（任意目的地一句 prompt 生成） | 深度优先：**3–5 座日本城市**，每座城市手工保证质量 |
| 客户端直连 LLM | 全部经服务端；游戏客户端不得持有任何 API Key |
| 浏览器 localStorage 足够 | 需要账号、多人会话、照片对象存储、云端存档 |

**保留其数据契约与后端骨架**，把渲染层、prompt 层、事实层全部换掉。

## 3. GAP 矩阵

### 3.1 总表

| 维度 | 现状 | 目标 | GAP | 严重度 | 处置 |
|---|---|---|---|---|---|
| **渲染 / 游戏内核** | React SPA + Google Maps 2D 滑图；无相机、无精灵、无场景 | Phaser 4.2.1 + 3–4 层俯视分层 2.5D，角色移动、场景切换、昼夜 | **100% 缺失** | 🔴 极高 | 全新建设（§4.4、§4.5） |

### 3.2 最危险的 GAP（必须最先解决）

| 排名 | 风险 | 为什么它能杀死项目 | 便宜的证伪方式 |
|---|---|---|---|
| **1** | **"游戏选择 → 现实行程"的映射质量** | 全部价值都押在这一条。如果游戏里玩一遍得到的行程，现实里排不通（时间不够、店休、换乘太复杂、预约不到），整个卖点归零。**这是产品假设，不是技术问题，写代码无法解决** | **纸上原型（1–2 天，零代码）**：选 1 座城市 10 个真实地点，手工排 1 日行程，用真实数据核对营业时间/交通/耗时，然后**真人实际走一遍** |
| **2** | **事实数据的成本与合规** | Google Places/Directions 的 ToS 对缓存与再分发有硬限制，若不能落库，每开一次游戏都在烧 API 费用，且离线不可用 | 读出 ToS 原文 + 算一次月度成本；确认 OSM/ODbL 或自建策展数据集能否替代 |
| **3** | **日本交通数据的可执行性** | 换乘是日本旅行最难的一环。若算不出可信换乘，只能深链 Google Maps/乘换案内，则"不用做攻略"的承诺打折 | 明确 MVP 是"自算"还是"深链"，并接受其 UX 代价 |
| **4** | **美术量产：多座城市的不同面貌** | 2.5D 每个新城市都要新的建筑/街道/地标资产。这是小团队最容易低估的成本 | 先只做**1 座城市的垂直切片**，量出"每座城市真实工时"，再决定是否扩到 3–5 座。用 §4.5 的"共享 tile 词汇表 + 每城风格包"纪律约束成本 |
| **5** | **范围膨胀复发** | 上一个项目正是死在这里——在"内测工具"上花了 3.7 万行 | 制度：**任何与"玩一遍→出攻略"闭环无关的功能，一律拒收** |

## 4. 架构规划

### 4.1 分层（事实与表达强制隔离 —— 这是全项目的架构红线）

```
┌─────────────────────────────────────────────────────────────┐
│ ① FACT LAYER（事实层）—— 只有它可以产出"地点/时间/票价/交通"      │
│   city-pack/  (git 管理的策展数据，每包一座城市)                  │
│     places.json       id, 名称(日/中/英), 坐标, 营业时间, 票价     │
│     transit.json      线路/站/换乘/耗时/费用                     │
│     districts.json    场景分区、可行走区域边界                    │
│     每个事实字段必须带: source(URL) + verified_at(日期)          │
│   provenance/         抓取与人工复核记录                         │
└──────────────────────┬──────────────────────────────────────┘
                       │ 只读、只注入、不可修改
┌──────────────────────▼──────────────────────────────────────┐
│ ② SIMULATION LAYER（游戏世界）—— 消费事实层，不创造事实           │
│   Phaser 3: 场景 / 角色 / 时间系统 / 交互 / NPC 位置              │
│   硬约束：世界的边界 = 事实层的边界。不许"程序化生成一个不存在的街区"  │
└──────────────────────┬──────────────────────────────────────┘
                       │ 玩家的选择 → 结构化事件流
┌──────────────────────▼──────────────────────────────────────┐
│ ③ ITINERARY LAYER（行程）—— 从游戏轨迹推导出可执行行程            │
│   纯确定性 TS 模块，无 LLM：                                     │
│     legs(骑行/步行/电车) + 时间约束 + 营业窗口 + 冗余缓冲          │
│   输出 GuideDoc（攻略）与它同源                                   │
└──────────────────────┬──────────────────────────────────────┘
                       │ 结构化事实载荷（只读）
┌──────────────────────▼──────────────────────────────────────┐
│ ④ NARRATIVE LAYER（叙事）—— LLM 只在这里，绝不产出事实            │
│   输入: GuideDoc 的只读 JSON（事实已固定）                        │
│   输出: 风味文本 / NPC 台词 / 文化解说 / 语言卡润色               │
│   强制: JSON Schema 校验 + 拒绝重试 + seed + 每会话成本上限        │
└──────────────────────┬──────────────────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────────────────┐
│ ⑤ PRESENTATION LAYER（React）—— 攻略手册 / 回忆录 / 多人 UI       │
│   与 Phaser canvas 通过事件总线松耦合；不共享 React 状态树         │
└─────────────────────────────────────────────────────────────┘
```

**红线落地方式（可机械检查）**：
- `src/narrative/**` 不得 import 任何 `city-pack/**` 的写入 API，只能接收已冻结的 `GuideDoc`；
- `GuideDoc` 中的事实字段为 `readonly`，TypeScript 层禁止 LLM 返回值写入事实字段；
- 服务端 `POST /api/narrative/wrap` 的入参 schema 与出参 schema 分离；出参只允许 `narrative` 命名空间下的字段；
- CI 检查：任何 `places.json` / `transit.json` 的改动必须带 `source` 与 `verified_at`，否则构建失败。

### 4.2 技术栈建议

| 层 | 选择 | 理由 |
|---|---|---|
| 构建 | **Vite + TypeScript** | 替换 react-scripts 5（同时消除 CRA 在 Node 26 上的不确定性、死 webpack 配置、`npm run analyze` 空转） |
| 游戏 | **Phaser**（建议 **4.2.1**，而非 3.90.0；理由见 §4.4） | 浏览器原生 + 对 React 18 安全 + TS 优先 + tilemap 级能力；且它没有 reconciler，是唯一不与 React 18 冲突的选项 |
| 视觉档位 | **3–4 层俯视分层（top-down layered）**（见 §4.5） | 唯一"成本随 *tile* 复用而摊薄"而非随 *画面数* 线性增长的档位；且与"关卡片区 = 真实地图几何"直接对齐 |
| UI | React 18 + 现有 MUI 5 | 攻略手册、回忆录、时间线可复用旧 UI 骨架 |
| 桥接 | 单一 `GameEventBus`（Phaser Events ⇄ React 订阅） | 避免 React state 与游戏循环互相驱动；StrictMode 双挂载下游戏实例只创建一次 |
| 后端 | Node 20/22 LTS + Express（沿用） | 旧骨架可搬；**不要用 Node 26 跑 CRA，若因故保留 CRA 则需 Node 18/20** |
| 事实数据 | 三层新鲜度 + 策展式 city-pack | 见 §4.3、§3.2 风险 2 |
| 持久化 | 先 SQLite/Postgres + 文件存储（S3/R2 兼容），后视需要 | 旧项目 mongoose 已 UNMET 且无服务使用，不要盲目继承 |
| 多人 | 后期；候选 Socket.IO / Colyseus | **在做通单人闭环之前不碰** |

### 4.3 攻略数据契约（从旧契约升级）

旧契约（`travel_split_by_day → dairy_routes`）的字段是：`route_id / departure_site / arrival_site / departure_time / arrival_time / user_time_zone / transportation_type / duration / duration_unit / distance / distance_unit / recommended_reason`。

**保留其骨架，补齐四类可执行性字段**（这是"能照着走"与"看起来像行程"的区别）：

| 新增字段类别 | 具体字段 | 解决什么 |
|---|---|---|
| 真实性溯源 | `source_url`, `verified_at`, `confidence` | 用户能判断"这条信息多新、能不能信" |
| 换乘细节 | `line_name`, `station_ja`, `platform_hint`, `ic_fare`, `ticket_fare`, `transfer_count`, `walk_minutes` | 日本旅行的真正难点 |
| 冗余与兜底 | `plan_b`（替代地点/替代时段）, `buffer_minutes`, `booking_required`, `closed_days` | 店休、满员、排队 |
| 跨语言与无障碍 | `name_ja`, `name_zh`, `name_en`, `phrase_card`, `accessibility_notes` | "不因文化差异害怕" |

**每个叶子节点都必须能回答："玩家凭什么相信它？"** 答不上来的字段不允许进入攻略。

### 4.4 引擎版本：建议用 **Phaser 4.2.1**，而不是 Phaser 3

**这是本规划中唯一一条建议你改变原始选择的地方**，理由是可复现的版本事实（我独立从 npm registry 元数据复现）：

| 事实 | 值 | 来源 |
|---|---|---|
| Phaser 3 最后一个版本 | **3.90.0**，发布于 **2025-05-23** | `docs/handOff/archive/engine/npm_phaser.json` 的 `time` 字段 |
| Phaser `latest` | **4.2.1**，发布于 **2026-07-09** | 同上 `dist-tags.latest` |
| Phaser 4.0.0 发布 | **2026-04-10** | 同上 `time` 字段 |

即：Phaser 3 分支已 **约 16 个月没有新版本**；`npm i phaser` 现在装到的是 4.2.1。

**关键取舍（决定"美术档位"必须先于"引擎版本"定下来）**：
- Phaser 4 **移除了 `Mesh`、`Plane`、`Camera3D`、`Layer3D` 且无直接替代** —— 这砍掉了 Phaser 3 里做"伪 3D/等距"的逃生通道；
- Phaser 4 新增的 `TilemapGPULayer` 官方定位是 **"仅正交（orthographic）tilemap，不适用于等距或六边形地图"**。

**结论**：Phaser 4 的定位与 §4.5 建议的**俯视分层**档位**天然吻合**，但**与真等距（isometric）艺术不兼容**。
→ 若你坚持真等距美术：要么留在 Phaser 3 + 自己写等距渲染，要么换 Three.js + R3F，但后者要求 **React 19**（见下）。
→ 若接受俯视分层（我建议接受）：**直接用 Phaser 4.2.1**。

**另一面墙（已独立复现，务必知道）**：
- `@pixi/react@8.0.5` 的 peer 是 **`react >=19.0.0`**；官方 v8 发布文直言"为 React 19 专属设计"，并承认对 React 18 用户"升级路径存在显著障碍"。
- `@react-three/fiber@9.8.1` 的 peer 是 **`react >=19 <19.4`**。
- **所以：如果继续用 React 18，Phaser 是唯一没有 reconciler、因而不会与 React 冲突的选择。** 想换 Pixi 8 或 R3F，等于同时要把项目升到 React 19——这是"两件事"，不是"一件事"。

**什么情况下应该推翻这个建议**：
- 确定为真等距美术 → 换 Three.js + R3F，并把 React 升到 19；
- 实测 Phaser 4 生产包体 **> 1.5 MB gzip** → 重新评估 PixiJS v8 + React 19 路线。

**WebGPU 不作为目标**：Pixi 官方把 WebGPU 标为"实验性——生产请用 WebGL 渲染器"；caniuse 显示全球支持约 85.7%，且 Firefox 到 159 仍默认关闭。**目标 WebGL。**

### 4.5 视觉档位：建议 **3–4 层俯视分层（top-down layered）**

四个档位的对比（详细论证见 `recon-2.5d-game-research.md` §2）：

| 档位 | 成本随什么增长 | 对"5 座不同城市"的可扩展性 | 判定 |
|---|---|---|---|
| 等距 tile（isometric） | 可见面数（每个 tile 要画 3 个面） | **最差** | ✗ |
| **3–4 层俯视分层** | **tile 种类（可复用）** | **最好** | ✅ **建议** |
| 2D 精灵 + 3D 场景（HD-2D） | 两套管线（美术 + 三维） | 差 | ✗ |
| 预渲染背景 + 3D 角色 | 画面数（每屏都要新画） | 最差 | ✗ 直接排除 |

**为什么俯视分层还额外契合本项目**：它和 §2.3.1 的"关卡即真实地理"是同一件事的两种说法——俯视地图的几何**可以直接来自真实地图数据**（街道拓扑是二维的），不需要等距投影转换。等距美术反而会在"事实几何 → 游戏几何"之间插一道手工转换。

**美术纪律（写进评审清单）**：
> 一套**共享 tile 词汇表** + 每座城市一个**风格包**（调色板 + 招牌字体 + 6–10 个街区道具）。
> **如果新增一座城市需要一个新的 tile 类型，那是设计缺陷，不是美术任务。**

这条纪律是"3 座城市"与"5 座城市"之间成本能否受控的分水岭。

#### 4.5.1 素材许可的陷阱（已取证，直接影响能否商业化）

选素材时必须逐个查许可，存在一个**会让整个美术层被传染**的陷阱：

| 素材源 | 许可 | 对本项目的影响 |
|---|---|---|
| **Kenney** 城市套件 | **CC0** | ✅ 可商用、无需署名。最安全的起点 |
| **Liberated Pixel Cup (LPC)** | **CC BY-SA 3.0 / GPL 3.0 双许可** | ⚠️ **传染风险**：CC BY-SA 要求"演绎作品必须以相同许可分发"。本项目**必然要重新上色与重排 tile**，因此一旦使用 LPC，**我们自己的 tileset 也必须以 CC BY-SA 3.0 发布** |

**决策规则**：在选定任何免费素材包之前，先跑同一个测试——**"这份许可会不会传染到我们的 tileset？"** 若会，则要么放弃该素材，要么接受"tileset 必须开源"的后果（这会与商业发行的预期冲突）。商用日本城市素材包目前**查不到可获取的许可条款**，这仍然卡着美术预算。

#### 4.5.2 LLM 成本的一个结构性问题（已取证）

OpenAI 提示缓存默认开启，缓存输入最高 **90% 折扣**（写入 1.25×、读取 0.1×）。**关键推论是"顺序决定账单"**：

- 把**稳定不变的 `GuideDoc` 放在 prompt 前面**，把每条 leg 的变化部分放在后面 → 10 次请求约为 **2.15×** 未缓存成本的量级；
- 顺序反了（变化内容在前）→ 缓存永不命中，约为 **10×**。

**架构含义**：这给事实/表达分层加了一条**成本上的**论证——事实层天然稳定、天然适合做缓存前缀，而叙事层天然多变。分层不只是正确性设计，也是省钱设计。

## 5. 分阶段实施规划

### 阶段 0 — 7 日证伪：**不写一行引擎代码**，先证明玩家真的会用这份攻略 **最高优先级**

**风险最高的假设（本项目的生死假设）**：
> 玩家会真的导出攻略，并在现实旅行中使用它，从而改变实际决策。

这个假设**可以用一份打印文档杀死，不需要引擎**。越早杀死越好。

| 天 | 动作 | 产出 |
|---|---|---|
| 1 | 手工策展**一个真实街区**的 30 个 POI，每个字段带 `source` + `verified_at`；**每个地点的 source 必须真正打开读过** | `places.json`（手写即可） |
| 2 | 手工写一份**确定性攻略**：纯模板生成，**不含任何 LLM、不含游戏**，可打印 | 一份真能照着走的文档 |
| 3 | 做一屏"游戏观感"的假图（**只为让受试者理解产品形态，不是原型**） | 一张静态画面 |
| 4–5 | 交给 **3 个真的要去那里旅行的人** | — |
| 6 | 复盘：他们用了哪条？哪条改变了决定？哪条他们不信？ | 复盘记录 |
| 7 | 决定：继续 / 改范围 / 停 | 决策记录 |

**必须同时记录的第二个数字：每个地点的策展耗时（分钟/地点）。**
若 > 20 分钟/地点，则 150 个地点的城市包在人力上不可行。这个失败模式**在有人照着错误营业时间白跑一趟之前是看不见的**，所以必须和"攻略有没有用"一起测。它同时给出城市包规模的**人力上限反推**。

**通过标准（写死，避免自我说服）**：
- ✅ 3 人中**至少 2 人**用它做出了一个"否则不会做"的决定；
- ✅ 3 人中**至少 1 人**主动索要另一座城市的同类文档。

**不通过怎么办**：
- 攻略**被读但没被用** → "导出攻略"是**功能**不是**产品**；应围绕他们**实际做的事**重新定范围（按证据判断，很可能是回忆录那条线）。
- 攻略**根本没被打开** → 问题在"游玩→导出的动机"，回到 §2.3.1 的目标引导设计，**不是回到引擎**。
- **两种情况下都不要开始写引擎代码。**

**通过后交付**：10–20 行的《映射规则说明》——"在游戏里做了什么动作，会变成攻略里的什么条目"。它定义整个项目的产品核心，也是阶段 3 的验收依据。


### 阶段 1 — 事实地基（2–3 周，无 LLM、无渲染）

- 定义 `city-pack` schema 与溯源纪律（`source` + `verified_at` 必填）。
- 三层新鲜度制度：**静态层**（地址/坐标，一次策展长期有效）／**半静态层**（营业时间，季度复核）／**动态层**（临时休馆/活动，运行时查询或标注"请出发前确认"）。
- 建立 **1 座城市**的完整数据包 + 校验脚本。
- 明确合规结论：数据从哪来、能不能落库、能不能分发（见 `recon-geodata-reality.md`）。
- 交通换乘：先做**"深链 + 手工策展常用路线"**，不做全网算路（成本与复杂度都不可控）。

**出口标准**：能输出一份机器可校验、人可阅读的行程 JSON，其中**每个事实都有来源和验证日期**。

### 阶段 2 — 技术骨架（2–3 周）

- Vite + TS + React + Phaser 3 骨架；单一 `GameEventBus`；StrictMode 安全。
- JSON Schema 校验层（用 zod/ajv），失败即拒绝，不做静默降级（旧项目的 `{raw_content, error}` 静默降级必须避免）。
- 服务端代理 + 密钥全在服务端；客户端不得有任何 key。
- 存档系统（本地 + 可选云）；调试覆盖层（FPS / 时间 / 当前行程 / 事件流）。
- 从旧项目搬入：`server/routes/googlemaps.js`、代理骨架、vault(local 后端)、rateLimit、logger、离线三件套、Timeline UI。

**出口标准**：一条命令本地跑起来；能进入一个空场景、走动、切场景、存档读档。

### 阶段 3 — 垂直切片：第一座城市（4–6 周）**第一个可玩里程碑**

- 1 座城市、1 个可探索区域、8–12 个真实地点、1 条 1 日主线。
- 接入时间系统（昼夜/营业窗口）、步行 + 电车、行程记录。
- **一键导出攻略**（第一版：结构化手册，可打印/可离线）。
- **回忆录 v1**（行程 + 玩家在游戏里的"拍照"记录）。
- 端到端验收（**双门槛，缺一不可**）：
  1. **可玩性门槛**：一个没听过这个项目的人，从零开始玩 30 分钟**不被告知"这是为了生成攻略"**，玩完表示"想继续玩"（而不是"这有什么用"）。
  2. **可执行性门槛**：导出的攻略交给另一个真人照着走，能走通。

**出口标准**：闭环成立 **且游戏自身成立**。这是整个项目的生死线。
**注意**：门槛 1 不通过时，**不要**靠加班加功能去救，要回到关卡与目标引导设计（§2.3.1）重新想。

### 阶段 4 — 现实照片回流（2–3 周）

- 照片上传（浏览器端 EXIF 解析 + 客户端压缩）。
- EXIF 时间/GPS → 与游戏日程对齐 → 自动归入"第几天/哪个地点"。
- 回忆录排版（虚拟截图 + 现实照片混排）。
- 法规与同意流程（人脸/隐私、APPI/GDPR 提示）。

**出口标准**：拿真实旅行照片跑通一次"上传 → 对齐 → 生成相册"。

### 阶段 5 — LLM 叙事层（2–3 周，仅在有事实层之后）

- `POST /api/narrative/*`：输入冻结的 `GuideDoc`，输出叙事文本。
- 强制：JSON Schema + 拒绝重试 + seed 确定性 + 每会话 token 预算 + 成本记账 + prompt 注入防护 + 流式输出。
- Prompt registry（集中管理，禁止字面量散落）。
- 内容审查（NPC 台词面向玩家，需 moderation）。

**出口标准**：关掉 LLM 后游戏依然完整可玩（**这是"LLM 是调味料不是主料"的机械证明**）。

### 阶段 6 — 多人合作（3–4 周，可选）

- 1–4 人同会话：共享行程、看到彼此位置、投票决定下一步。
- 先做"同屏异步"（共享状态 + 轮询）再考虑实时。

**出口标准**：两人能一起玩完一条 1 日主线并共同导出一份攻略。

### 阶段 6.5 — 收集与目标引导系统（2–3 周）

**为什么单独成阶段**：它不是"润色"，而是**目标引导的载体**（§2.3.1）与**变现的入口**（§2.3.2）。放在单城闭环之后、多人之前最合适。

- 图鉴 / 旅行印记 / 徽章系统：每地点一枚，集齐一城解锁章节。
- 收集进度与"我还没去过的地方"清单（这同时就是攻略的骨架）。
- 收集品的**实体化出口设计**（先设计兑换路径与 SKU 结构，不急着做物流）。
- 章节解锁与解锁条件的现实约束校验（不能解锁一个"营业时间冲突"的关卡）。

**出口标准**：收集欲成立 —— 测试者主动说"我想集齐这一区"。这是留存的最早可信信号。

### 阶段 7 — 扩到 3–5 座城市（每城 3–5 周，视阶段 3 实测成本而定）

**入口条件**：阶段 3 的"每座城市真实工时"已量出，且总预算允许。
**做法**：内容管线 + 场景模板化（避免每城从零做美术）。

### 阶段 8 — 发布准备（仅当决定对外）

存档迁移、离线包、性能、无障碍、法务免责与"出发前确认"提示、多语言。

### 工期现实性检查

> **行业基准（已取证，2026-09 补）：** 早先这节标注为"无法取证"，现已用 `curl` 取到四个可比案例（`web_fetch` 工具被拦，但 `curl` 能出网且逐站可用性不一）。**结论比原先的假设更严重：估算普遍偏差约 2 倍。**
>
> | 案例 | 团队 | 计划 → 实际 | 来源 |
> |---|---|---|---|
> | Stardew Valley | 1 人 | **4.5 年** | [gamedeveloper.com](https://www.gamedeveloper.com/production/how-i-stardew-valley-i-creator-eric-barone-coped-with-a-four-year-dev-cycle) |
> | A Short Hike | 1 人 + 亲友 | "数月"，但**自设 3 个月死线**且**复用了废弃项目的脚本与素材** | [Wikipedia](https://en.wikipedia.org/wiki/A_Short_Hike) |
> | Unpacking | Witch Beam（成熟工作室） | **估 1.5 年 → 实际约 3 年**（"实际制作花了两倍时间"） | [Wikipedia](https://en.wikipedia.org/wiki/Unpacking_(video_game)) |
> | 80 Days | inkle，**核心 3 人** | **估 3 个月 → 实际 9 个月**；内容 20–30 城 → **100+ 城** | [gamedeveloper.com](https://www.gamedeveloper.com/business/postmortem-inkle-s-i-80-days-i-) |
>
> **两条直接影响本规划：**
> 1. **"数月"档位只在小世界 + 复用代码时成立**——本项目两者都没有。80 Days 那 3 人的 AAA 经验作者原话是"这是我们俩做过最难的项目"，并在 20 万字处发现"它不好玩，而我们不知道为什么"。
> 2. **估算偏差约 2 倍**：所以下面的 24 周方案应当读作 **12 周方案**，或把目标砍半。
>
> 唯一的反例（A Short Hike 数月完成）恰恰印证了这一点：它靠的是**复用废弃项目 + 极小的世界 + 自设死线**。
>
> **⚠️ 证据强度标注（事后补充）**：上表数字来自 `iteration/recon/recon-2.5d-game-research.md` §6.1.1，
> 每行都带具名出处与直接引语（80 Days 的 "20–30 城 → 一百多城"、Unpacking 的 "实际制作花了两倍时间"）。
> 但另有一份更严格的同期检索（`docs/project_lifecycle/knowledge/_recon_tmp/q4q6-hardproblems-scope.md` §Q6.1）
> 把 **Stardew 的 2012 起始**与 **Unpacking 的开发时长**标为 `UNVERIFIED`——因为它只承认自己本次抓到的原始来源。
>
> **两者不矛盾**：差异是"是否接受二手转述"，不是事实冲突。但结论稳健性应据此分级：
> - **最强**：80 Days（3 个月计划 → 9 个月实际，内容超额 4–5 倍）——具名媒体出处 + 逐字引语；
> - **次之**：Unpacking、Stardew——来源可信但属二手转述。
>
> 因此"**估算偏差约 2 倍**"这条结论我保留，但它只建立在 **2 个**案例上（80 Days、Unpacking），
> **样本量小**。请把"24 周读作 12 周"当作**风险提示**，而不是精确系数。

| 里程碑 | 乐观假设 | 规划假设（1 人 + AI） | **按 2× 偏差校正后** |
|---|---|---|---|
| 阶段 0–1（证伪 + 事实地基） | 2 周 | 3–5 周 | **4–8 周** |
| 阶段 2–3（骨架 + 单城闭环） | 5 周 | 8–12 周 | **10–20 周** |
| 阶段 4–6.5（照片 + 叙事 + 收集） | 7 周 | 10–16 周 | **14–26 周** |
| 单人完整 MVP（阶段 0–6.5） | 14 周 | 21–33 周 | **28–54 周** |
| 3–5 座城市 | +6 周 | +12–25 周 | **+20–40 周** |

**请把阶段 3 当作唯一必须到达的里程碑**，其余都是可选项。阶段 3 一旦完成，"每座城市真实工时"就被量出来了，届时再决定是否扩城。

> **新增的一个隐形失败模式（必须一起测）**：策展每个地点的耗时。若 **> 20 分钟/地点**，则 150 个地点的城市包在人力上不可行——而这个失败模式**在有人照着错误营业时间白跑一趟之前是看不见的**。所以阶段 0 的 7 日证伪里必须**同时记录每个地点的策展耗时**。

## 7. 工程纪律纠正（针对旧项目的制度性病因）

旧项目不是被 bug 杀死的，是被**这五个习惯**杀死的。新项目必须显式反对它们：

| # | 旧习惯 | 新纪律 |
|---|---|---|
| 1 | 先建流程（问卷/看板/审计/会话录制），后建产品 | **任何与"玩一遍→出攻略"闭环无关的功能，一律拒收。** 第一个可玩闭环优先于一切基础设施 |
| 2 | 文档宣称 ≠ 代码事实（`ARCHITECTURE.md` 说 key 不暴露，实际内联进 bundle） | 文档中每个能力声明必须附**可执行验证命令**；不可验证的声明不得写进文档 |
| 3 | 测试通过 ≠ 产品可用（安全网挂在死模块上） | 测试必须指向**应用实际 import 的模块**；CI 加一条检查：测试文件的被 import 目标必须与运行时代码同一路径 |
| 4 | 用"文件行数/阶段完成率"衡量进度 | 用**"实现该功能的唯一验收路径"**衡量：第一是"能不能玩 30 分钟并导出攻略"，其余都是次要指标 |
| 5 | 大而全（多环境/多云/多角色/多语言/无障碍/AR/订阅制全写进 README） | **深度优先**：1 座城市做到可执行，再谈 3–5 座。README 只写已实现的 |
| 6 | 把游戏当"攻略的包装" | **游戏优先**（§2.3）。验收同时看"好不好玩"与"攻略能不能用"。只卖收藏与表达，**不卖时间与捷径** |

### 7.1 付费设计的真实性红线（写进代码评审清单）

以下机制一律禁止，因为它们让"游戏内成本 ≠ 现实成本"，从而让自动导出的攻略变得不可执行：

- ❌ 付费加速 / 跳过等待 / 快速传送 / 免排队
- ❌ 付费增加"一天的时间"或"更大的行李容量"
- ❌ 用抽卡随机决定真实地点的出现（真实地点不是奖品，是事实）
- ❌ 把"能用的攻略"整体锁在付费墙后（会让 §2.3 的 C4 崩塌）

**允许**：外观、装扮、相册主题、实体周边、城市扩展包、多人协同、预约提醒、**耐久与数量类**（印制成实体书、第二座城市、实体纪念品）。

> **⛔ 修正（此前把"离线包"错列为允许项）：** 离线**不是增值项，是核心承诺的交付格式**。攻略必须能打印、能在无信号的手机上打开——否则"不用做攻略"这个承诺不成立。把它做成付费档会直接压垮 C4。**判据有两条**：
> 1. 这个付费点会不会改变游戏内的时间/费用账本？会 → 禁止。
> 2. 这个付费点是不是"成品能否打开/能否带走"本身？是 → 禁止。
>
> 付费只卖**收藏与表达**，以及**耐久与数量**；永不卖"这份攻略在没有信号时能不能看"。
