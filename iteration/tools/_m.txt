chore(vcs): a measured branching model, and the six defects that measuring it exposed

The stated model is master as production-only and iteration as the development line.
Rather than assert that from habit I checked the repository against the two authoritative
sources, and the check turned up more than a naming preference.

Measured reality:
  default branch      master   (there is no main, and no develop)
  iteration vs master 198 commits ahead
  remote branches     11, nearly all finished release/feature branches from 2025

Six defects, all traceable to branch names that do not exist:

1. FIVE workflows filter on main/develop, so they have never run - ci-cd, e2e-tests,
   security-scan, stability-tests and branch-protection. Per GitHub's documentation this
   is worse than inert: a workflow skipped by branch filtering leaves its checks in a
   Pending state, and a PR requiring those checks is blocked from merging.
2. branch-protection.yml configured protection for main and develop. The real branches had
   none, so nothing prevented a direct push to master.
3. workflow_dispatch requires the workflow file to be on the default branch, so
   fact-integrity.yml cannot be triggered manually while it exists only on iteration.
4. CONTRIBUTING.md told contributors to branch from main, a branch that does not exist.
   Their first step would fail.
5. Eight of 620 tracked text files were not UTF-8: four UTF-16LE, four with a BOM.
   CONTRIBUTING.md being UTF-16LE is plausibly why defect 4 survived unnoticed.
6. The branch name iteration collides with the top-level directory of the same name;
   'git log -1 iteration' fails with "both revision and filename".

Fixed: all workflow and protection branch references now name master/iteration; the 8 files
are clean UTF-8 with no BOM, and the 620-file sweep is now zero; CONTRIBUTING.md points at
iteration. The model, with per-claim sources, is iteration/design/branching-model.md.

Deliberately NOT done, and listed as yours to decide: pushing anything to master (that is
the one action the user reserved), branch protection changes (needs GitHub permissions),
and pruning the 11 remote branches (a release branch should be deleted only after its tag
exists, or the release record goes with it).

Sources: nvie.com GitFlow for the master/integration split and the release/hotfix
merge-back rules; GitHub's Triggering a workflow for branch filters, the Pending-check
consequence, and the default-branch requirement for workflow_dispatch; trunkbaseddevelopment.com,
cited because this project deliberately departs from it by keeping a long-lived development
branch - the cost is merge drag, and the mitigation is release cadence, not deleting the branch.
